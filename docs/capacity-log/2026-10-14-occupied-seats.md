# 2026-10-14 점유 좌석 API(C) 적용과 재측정

## 요약

P-011을 고치는 방법으로 사용자가 C를 골랐다. P-011은 200 u/s에서 PC CPU가 차서 DB 연결 대기가 생긴 문제다.

C는 좌석 상태 API를 바꾼다.
- 지금 API는 15,000석 전체를 보낸다.
- 새 API(`GET .../seats/occupied`, Core `1bf4baec`)는 점유된 좌석 번호만 보낸다.
- 03 흐름이 새 API를 부르게 했다(`41c3047`).

**한계가 150~200 u/s에서 300~400 u/s로 올랐다.** 200·250·300 u/s는 PASS, 400 u/s는 세 번 모두 FAIL이다.

- 사용자당 Core 메모리 할당이 7.7MB에서 2.5MB(200 u/s)로 줄었다.
- Core는 같은 7코어로 두 배의 사용자를 처리했다.

400 u/s에서 연결 풀(10)이 다시 찼다(P-013). 이번에는 연결을 한 번 쓰는 시간이 1.3ms로 짧다. 문제는 사용자 한 명이 연결을 빌리는 횟수(14번)다.

## P-012 400 u/s를 연달아 돌리면 Windows 임시 포트가 바닥난다

- **증상**: 진단 실행(세 번째 400 u/s)에서 73명이 좌석 조회 단계에서 응답을 못 받았다. Gatling 오류는 `j.n.BindException: Address already in use: getsockopt` 72건이다.
- **근거**: 측정 2분 뒤에도 Core 포트(8083)로 가는 TIME_WAIT 소켓이 8,070개 남아 있었다. Windows 임시 포트는 49152부터 16,384개다.
- **원인 후보**: Gatling은 이미 `shareConnections()`를 쓴다. 그래도 과부하로 동시 요청이 늘면 연결이 많아지고, 닫힌 연결이 TIME_WAIT로 남는다. 누가 먼저 연결을 닫는지는 확인하지 않았다(미확인).
- **판정 영향**: 앞의 400 u/s 두 번은 실패 0건으로 이미 FAIL이다. 결론은 같다.
- **400 u/s 위를 재려면** 둘 중 하나가 필요하다.
  - 실행 사이에 TIME_WAIT가 빠질 때까지 기다린다(run-step에서 사전 확인).
  - 부하 발생기를 다른 PC로 옮긴다.
- **도구 문제(다음에 본다)**: 결과 분류 이름이 `TECHNICAL_PERFORMANCE_SUMMARY_NO_RESPONSE`인데 마지막 단계는 `SEAT_STATUS`다. 분류 이름이 단계와 맞지 않는다.

  - 선점 저장 `saveIfAbsent` 43
  - 선택 저장 `selectIfAbsent` 15
- **체류가 시간이 갈수록 늘어난다**: 묶은 뒤 400 u/s 입장 5초 구간별 중앙값이 2.0 → 3.5 → 3.9 → 4.6 → 7.1 → 7.5초다.
  - 원인 후보: 점유 좌석 조회가 매 호출마다 Redis의 선택 목록(Lua 스크립트)과 선점 목록(`readAll`) **전체**를 읽는다. 실행 중 점유 좌석이 12,000석까지 쌓이므로 호출 한 번의 Redis 일이 시간에 따라 커진다.
  - Redis는 단일 스레드라 큰 명령 하나가 다른 모든 명령(락, 선점)을 늦춘다.
  - 명령별 Redis CPU는 재지 않았다(미확인). `INFO commandstats`를 실행 전후로 받으면 확인된다.
- **C의 부작용**: 좌석 15,000석을 DB에서 읽던 일이 점유 좌석 목록을 Redis에서 읽는 일로 옮겨 갔다. 판매 초반에는 가볍지만 점유가 쌓일수록 무거워진다.
