# 2026-10-19 로컬: 요청을 줄인 코드로 다시 오르고, 같은 날 이전 코드와 나란히 재다

## 요약

운영 50 u/s FAIL(사용자당 CPU 약 29ms)을 보고 사용자 한 명이 Core에 시키는 일을 줄였다(ticket `perf/core-capacity-request-cuts`, gatling `feat/capacity-03-fewer-requests`).
그 코드로 로컬 사다리를 10 u/s부터 다시 올랐다.

- **사다리**: 10~300 u/s PASS, **400 u/s FAIL**(FAIL 3번, 체류 p99 7.3·2.5·3.1초).
- 10-15의 이전 코드는 400·450 u/s를 PASS했다. 그래서 같은 날 같은 순서로 이전 코드(master `c653c6cf`)를 다시 쟀다. **이전 코드도 400 u/s FAIL**이었다(p99 19.7·6.3초). 오늘 PC는 10-15보다 느리다.
- 같은 날 비교에서 사용자 한 명의 일은 확실히 줄었다. HTTP 5 → 3번, 저장소 호출 20 → 12번, 연결 빌림 10 → 8번, Core CPU 18 → 14ms(약 −20%), Redis 명령 77 → 67~68개(−13%), 메모리 할당 1.0 → 0.71MB.
- 그런데 **로컬 400 u/s의 한계는 두 코드 모두 같은 곳이다.** DB 연결 풀 10개가 차고, 연결을 쥔 시간의 큰 몫은 쓰기 커밋이 WAL을 디스크에 내리기(fsync)를 기다리는 시간이다(10-15 결론과 같음).
  - 이번 변경은 읽기·CPU·Redis를 줄였고 쓰기 커밋은 그대로다. 사용자당 fsync 시간(2.1~2.8ms)이 이전 코드(2.3~3.1ms)와 거의 같다. 그래서 로컬 한계는 거의 움직이지 않았다.
  - 오늘 fsync 한 번은 1.5~3.1ms로 10-15(0.9~1.1ms)보다 길다. 그래서 400 u/s가 두 코드 모두 fsync 통로를 83~122% 써서 넘쳤다(10-15는 62%).
- **운영의 한계는 CPU다**(P-017, 2 vCPU). CPU −20%가 효과를 볼 곳은 운영이다. 운영 사용자당 29ms가 같은 비율로 23ms가 되면 50 u/s의 호스트 CPU는 (50 × 0.023 + 0.4) ÷ 2 = 78%로, 지금 40 u/s PASS 때(78%)와 같아진다. 그러면 첫 FAIL이 50 → 60 u/s로 오른다는 계산이다(미확인, 운영 측정 필요).

다음 수는 사용자가 정한다. 선택지는 맨 아래 "다음에 할 일"에 있다.

- 풀 예산: 400 u/s × 사용자당 연결 19~23ms = 7.6~9.1개분이다. 풀 10에 거의 붙어 있어 커밋이 조금만 밀려도 넘친다. fsync 통로 사용률은 400 × 2.1~2.4ms = 83~95%(이전 코드 91~122%)다. 10-15 이전 코드는 400 × 1.56ms = 62%였다.
- 리스너 스레드가 50~90개 떠서 요청과 같은 풀을 기다린다(P-015 그대로). 이벤트마다 새 스레드를 만드는 데 드는 `Thread.start0`가 커밋 직후(연결을 아직 쥔 동안) 요청 스레드에서 보였다.

**어떻게 발견했나**: 사다리 400 u/s FAIL 뒤 사용자당 지표를 이전 코드의 10-15 숫자와 비교하다가 연결 1회 사용이 1.2~1.8 → 2.3~3.3ms로 늘어난 것을 봤다. 코드 탓인지 날씨(그날 PC 상태) 탓인지 가르려고 같은 날 이전 코드를 같은 순서로 재서, 이전 코드도 같은 정도로 느려진 것을 확인했다.

## 발견한 문제

### P-021 로컬 WAL fsync가 날마다, 실행 간격마다 달라져 로컬 한계가 흔들린다

- **증상**: 같은 이전 코드가 10-15에는 400·450 u/s PASS, 오늘은 400 u/s FAIL 두 번이었다. 새 코드도 연달아 돌린 400 u/s(p99 7.3초)와 11분 쉰 400 u/s(2.5초)가 크게 달랐다.
- **근거**
  - fsync 한 번: 10-15 400 u/s 0.92~1.13ms → 오늘 1.54~3.11ms.
  - 연달아 돌린 10:46 실행은 3.11ms, 11분 쉰 10:57 실행은 1.66ms였다. 사용자당 fsync 횟수는 0.91 · 1.25번으로 오히려 연달아 돌린 쪽이 적었다(한 번에 더 많이 묶어 내렸다).
  - PG 체크포인트는 5분마다 2~3천 버퍼(약 24MB)를 4.5분에 나눠 쓴다. 측정을 흔들 크기는 아니다.
  - 기계는 같다(16 CPU, 힙 8GB). 다른 세션의 `byul-postgres`는 측정 중 CPU 0%였다.
- **원인 판단**: 로컬 400~500 u/s 한계는 WAL fsync 속도로 정해지는데(10-15), 그 속도가 PC·디스크 상태에 따라 2~3배 흔들린다. 앞 실행의 쓰기가 끝나기 전에 다음 실행을 시작하면 더 느려진다. 오늘 PC가 느린 이유(PG 컨테이너 재시작, WSL2 디스크, Windows 상태)는 미확인이다.
- **틀렸던 가설**: 실행 사이에 쉬는 이유를 "앞 실행 주문의 10분 만료 처리와 겹치지 않게"로만 보고, 만료가 겹치지 않으면 바로 다음 실행을 돌리게 바꿨다(10:43~10:46). 만료는 겹치지 않았지만 400 u/s의 fsync가 두 배 느려졌다. 쉬는 데는 디스크 쓰기가 가라앉는 몫도 있다.
- **해결 선택지**(측정 방법이라 사용자 결정)
  1. 코드 효과는 같은 날 A/B로만 판정한다(오늘 한 방식). 날짜가 다른 로컬 숫자는 "참고"로만 둔다. 장점: 지금 바로 된다. 단점: 실행 수가 두 배.
  2. 400 u/s 이상은 단계마다 PENDING 0까지 쉰다(10-15 규칙으로 되돌림). 장점: 조건이 일정. 단점: 단계마다 최대 10분.
  3. 실행 전후 `pg_test_fsync` 한 번으로 그날 디스크 속도를 기록한다. 장점: 날짜 간 비교 보정. 단점: 측정 도구에 단계 추가.
- **결정**: 대기.

## 측정 도구

- 이번 측정은 `run-step.ps1`을 작업용 루프 스크립트(저장소 밖)로 돌렸다. 루프의 변수 `$label`이 파라미터 `$Label`을 덮어써(PowerShell 변수 이름은 대소문자를 가리지 않는다) 사다리 행이 `warmup`으로 기록됐다. 라벨만 고쳤다.
