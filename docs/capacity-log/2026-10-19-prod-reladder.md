# 2026-10-19 운영 사다리 다시 오르기: 점검이 DB를 흔들었고, 고친 뒤 첫 FAIL은 초당 50명

## 요약

10-17과 같은 코드·데이터·호스트로 운영 사다리를 5 users/sec부터 두 번 올랐다.

첫 번째(07:36~07:46)는 **20 u/s에서 FAIL**했다(재현·진단은 PASS). 실행마다 부하 첫 10~20초에 DB 쿼리가 모두 느렸다.
원인은 측정 도구였다. `run-step -Prod`가 실행 직전마다 운영 DB에서 회원 100만·주문 500만 건을 끝까지 읽는 점검을 돌렸다(P-020).
같은 때 막 켠 Core의 메모리가 스왑으로 밀려나 연결을 쥔 채 멈추는 일도 겹쳤다(P-019).

점검을 실행마다 DB에 묻지 않게 고친 뒤(사용자 결정: 운영 점검은 최소로) 두 번째(08:04~08:12)를 올랐다.
5~40 u/s는 모두 PASS했고, 첫 20초 DB 지연은 사라졌다(p90 25~88ms → 1.1~2.2ms). **첫 FAIL은 50 u/s**다(세 번 모두 FAIL).
모양은 10-17의 P-017(호스트 CPU 포화)과 같고 10 u/s 낮다. 사용자당 Core CPU가 10-17보다 많고(37~40ms, 10-17 30ms),
같은 구간에 스왑 페이지 폴트(P-019)와 JIT 재컴파일이 겹쳤다.

다음 수는 사용자가 정한다: 40~50 u/s를 지금 사양의 한계로 보고 좁힐지, P-017·P-019(CPU·메모리)를 먼저 다룰지.

## 목적

10-17 첫 운영 측정(60 u/s FAIL, P-017)을 같은 조건에서 처음부터 다시 재서, 결과가 다른 날에도 같은지와 `run-step.ps1`이 새 판정 기준을

## 발견한 문제

### P-019 운영 호스트 메모리가 모자라 부하 중 Core 메모리가 스왑으로 밀려나고, 페이지 폴트 동안 연결을 쥔 채 멈춘다

**증상**: 20 u/s 첫 실행에서 07:42:21~24에 연결 대기가 17 → 81, 바쁜 요청 스레드가 82까지 올랐다. 같은 3초 동안 Core CPU는
0.08~0.42로 오히려 떨어졌다. CPU가 차서 느려진 것이 아니라 무언가를 기다리며 멈춘 모양이다. Gatling 쪽 요약 p99 2,035ms,
주문 생성 p95 1,936ms로 FAIL했다.

**근거**

| 항목 | 10-17(60 u/s까지) | 10-19(20 u/s까지) |
| --- | --- | --- |
| Core RSS(`container.memory.rss`) | 부하 전 640MB → 60 u/s 818MB | 기동 2분 뒤 800MB → 20 u/s 940MB |
| Core 스왑(`container.memory.swap`) | 최대 11MB | 6MB(07:37) → 215MB(07:43) → 237MB(07:46) |
| Core 메이저 페이지 폴트(초당) | 거의 0(한 번 40) | 5 u/s 0~1, 10 u/s 7~18, 15 u/s 64~198, 20 u/s 97~251, 재현 119~209, 진단 5~9 |
| 호스트 스왑(`system.swap.used`) | 214 → 260MB | 131MB(07:28) → 405MB(07:43) |
| JVM 힙 committed / non-heap committed | 155~210MB / 179~185MB | 156~217MB / 172~185MB |

- JVM이 보고하는 힙과 non-heap은 두 날이 같다. 차이는 그 밖의 네이티브 메모리(스레드 스택, JIT 컴파일러, GC 자료구조, Datadog 에이전트 등)다. 오늘은 JIT이 아직 많이 돌았다(실행마다 13~25초).
- 07:42:20~30 Datadog 스팬: Redis 호출 p90 31ms·최대 200ms(평소 1~2ms), DB 쿼리 p90 11.6ms·최대 342ms. Redis는 같은 호스트에 있으므로, Redis까지 같이 느리면 Core나 호스트가 멈춘 것이다.
- 느린 요약 조회 트레이스 `6ad54b4d000000000c14ca58b8092394`(2,182ms): DB 쿼리 3개는 합쳐 약 11ms이고, 첫 쿼리 전에 약 2.1초를 기다렸다. 연결을 얻기까지 기다린 시간이다. 연결을 쥔 스레드가 Core 안에서 멈춰 있었다.
- EC2 CPU steal은 평균 0.35%·최대 3.2%, iowait는 실행 중 2~4%다. CPU 크레딧 제한은 아니다.
- 계산: 20 u/s 연결 1회 점유 (278.556 − 166.942) ÷ (17,981 − 11,949) = 111.614초 ÷ 6,032번 = **18.50ms**. 연결 대기 (283.196 − 13.755) ÷ 6,032 = **44.7ms**. 재현은 8.93ms·6.2ms.

**원인 후보** (가능성 높은 순)

1. 호스트 메모리 부족 → Core 스왑 → 페이지 폴트로 요청 스레드가 연결을 쥔 채 멈춤. 호스트 1.9GB에 Core(RSS 800~940MB), Datadog Agent(약 125MB), FE(57~145MB), Redis·nginx·OS가 함께 있다. Core에는 `-Xmx`도 컨테이너 메모리 제한도 없다.
   - 지지: 폴트가 많은 15·20 u/s에서 연결 점유가 늘었다. 멈춘 3초 동안 CPU가 떨어지고 Redis까지 느려졌다. 10-17에는 Core 스왑과 폴트가 거의 없었다. 폴트가 적은 진단 실행(5~9/초)은 PASS했다.
   - 반대·미확인: 재현 실행은 폴트가 119~209/초였는데도 PASS했다(연결 대기 최대 25). 폴트가 많으면 반드시 FAIL하는 것은 아니다. 어느 스레드가 폴트를 내는지는 덤프가 없어 모른다.
2. Core가 덜 데워졌다(P-005의 운영판). 실행마다 JIT 컴파일 13~25초, 사용자당 CPU 136 → 47ms로 실행마다 줄어든다. 10-17은 배포 뒤 약 1시간 지나 시작했다.
   - 지지: 같은 20 u/s에서 첫 실행만 FAIL했고 뒤 두 번은 PASS했다.
   - 반대: 10-17도 같은 순서(예열 → 5 → 10 → …)였고, 그날 10 u/s 사용자당 CPU(87ms)도 오늘(82ms)과 비슷했다.
3. P-020(실행 시작 DB 지연)이 첫 10초에 쌓은 적체가 멈춤과 겹쳤다. 20 u/s 첫 10초 DB p90은 88ms였다.

코드·설정 위치:

- Core JVM 옵션: 운영 호스트 `/home/ubuntu/docker-compose.yml`의 `JAVA_TOOL_OPTIONS`(`-Xmx`·`MaxRAMPercentage` 없음), 컨테이너 `mem_limit` 없음.
- 이미지: ticket `Dockerfile`(`eclipse-temurin:25-jre-alpine`), Datadog 자바 에이전트를 같은 JVM에 붙인다.

**해결 선택지**

- **Core JVM 메모리 상한 정하기**(`-Xmx`나 `-XX:MaxRAMPercentage`, `-XX:ReservedCodeCacheSize`, 스레드 스택 `-Xss`) — 장점: 설정만 바꾼다, Core가 쓸 몫이 예측 가능해진다 / 단점: 힙 밖 네이티브 메모리는 이것만으로 다 묶이지 않는다. 너무 작으면 GC가 잦아진다 / 기대: RSS 증가가 줄어 스왑이 덜 난다(미확인). 어디에 쓰는지 먼저 보려면 `-XX:NativeMemoryTracking=summary`를 켜야 하는데 JRE 이미지라 `jcmd`가 없다.
- **같은 호스트의 다른 컨테이너 줄이기**(측정 동안 FE·Datadog Agent 끄기, 또는 다른 호스트로) — 장점: 약 180~270MB를 돌려받는다 / 단점: 측정 중 Datadog 지표·트레이스가 사라진다. 운영 구성과 달라진다 / 기대: 같은 사양에서 스왑이 줄어 10-17 수준(50 u/s PASS)으로 돌아올 것(미확인).
- **메모리가 큰 인스턴스**(2GB → 4GB) — 장점: 원인에 바로 닿는다. P-017(CPU)도 같이 풀려면 vCPU가 더 많은 유형 / 단점: 비용 / 기대: 스왑이 사라진다. 그 뒤 한계는 P-017(CPU)이다.
- **측정 규칙으로 우회**(Core를 켠 뒤 일정 시간·일정 부하로 데우고 시작, 스왑이 0인지 확인하고 시작) — 장점: 측정 조건이 날마다 같아진다 / 단점: 운영에서 실제로 겪을 "막 켠 서버" 상황은 가린다 / 기대: 오늘과 10-17의 차이가 줄어든다.
- **스왑 끄기**는 권하지 않는다. 메모리가 모자라면 멈춤 대신 OOM으로 Core가 죽는다.

**다음 실행**: 사용자가 메모리 쪽을 고르면, P-020을 가린 뒤 같은 조건(예열 → 5 u/s부터)으로 다시 오른다. 실행마다 Datadog에서 `ticket-be` 스왑·폴트가 0 근처인지 함께 기록한다.

**어떻게 발견했나**

1. 50 u/s 실행 표에서 다섯 요청이 함께 5배 넘게 뛰었다. 공용 자원 문제로 봤다.

### 50 u/s 원인 더 나누기: Core가 사용자당 CPU 약 29ms를 쓰고, 2 vCPU로는 약 50명이 한계다

**누가 CPU를 썼나** (Datadog `container.cpu.usage`, 50 u/s 부하 중 08:10:10~30 KST, 단위 코어)

| 컨테이너 | CPU |
| --- | --- |
| `ticket-be`(Core) | 1.72 (user 1.38, system 0.34) |
| `ticket-redis` | 0.10 |
| `ticket-nginx` | 0.08 |
| `datadog-agent` | 0.06 |
| `ticket-fe` | 0.00 |
| 합계 | 1.96 / 2.0 |

**계산**

- 포화 전 사용자당 Core CPU: 20 u/s 29.5ms, 30 u/s 27.7ms, 40 u/s 29.9ms(10-17 50 u/s 30.1ms). 약 29ms로 본다.
- Core 밖에서 쓰는 CPU: 컨테이너(Redis·nginx·Agent) 0.24코어에 커널(네트워크 처리)·dockerd·sshd(지표 터널)를 더해 약 0.4코어다. 호스트 `system_cpu`(0.96)와 Core `process_cpu`(0.75)의 차이 0.21 × 2코어로 잡았다.
- Core가 쓸 수 있는 CPU: 2.0 − 0.4 = 1.6코어. 1.6 ÷ 0.029초 = **이론상 최대 약 55 u/s**(CPU 100%).
- CPU가 80%를 넘으면 CPU 차례를 기다리는 줄이 길어져 응답이 무너진다. 호스트 CPU는 40 u/s 0.82(PASS), 50 u/s 0.96(FAIL)이었다(바쁜 표본 평균). 10-17 50 u/s(PASS)는 경계에서 겨우 버텼다.
- 넘은 뒤에는 사용자당 CPU가 37~40ms로 늘어 처리량이 더 떨어진다. Core 스레드 146 → 297개(요청 스레드 200개가 2 vCPU를 나눠 씀), system CPU 0.34코어(스왑 폴트 처리 포함, P-019), GC 동시 단계 시간 증가(재현 실행 3.0초).
- 연결 풀은 한계가 아니다. 포화 전 50 u/s 예산은 50 × 10회 × 2.5ms = 1.25(풀 10의 12.5%)다. 50 u/s의 연결 대기는 CPU를 기다리며 연결을 쥔 결과다.

**틀렸던 가설**: JIT 재컴파일이 CPU를 더 썼다고 봤다. 50 u/s 실행의 컴파일 시간은 24.8초였지만 코드 캐시(`CodeHeap 'non-profiled nmethods'`)는 18.38 → 18.83MB로 0.45MB만 늘었다. 재현은 0.05MB다. 컴파일러 스레드가 CPU 차례를 기다린 경과 시간이다(원인이 아니라 결과).

**미확인**: 29ms가 코드의 어디에 쓰이는지. 운영 Core의 Datadog 프로파일러는 켜져 있다(Agent가 1분마다 프로파일을 보냄, 50 u/s 구간에 분당 약 4.4MB). 처음에 스팬 태그만 보고 꺼졌다고 판단한 것은 틀렸다. 프로파일은 Datadog API(MCP)로 읽을 수 없어 웹 화면(APM → Profiles)으로 본다. 지금 아는 사용자 한 명의 양: HTTP 5번, 저장소 호출 20번, 연결 빌림 10번, 메모리 할당 1.49MB, 로그 0건(40 u/s 전후 차이).

**늘리는 선택지**(기대값은 위 계산을 그대로 쓴 추정, 미확인)

1. **vCPU 늘리기**(2 → 4): Core 몫 약 3.6코어 ÷ 0.029 = 이론 약 124, 80% 기준 (3.2 − 0.4) ÷ 0.029 = 약 97 u/s. vCPU는 하이퍼스레드라 정확히 2배가 아닐 수 있다. 메모리도 함께 늘리면 P-019도 풀린다. 그다음 한계 후보는 RDS(인스턴스 클래스 미확인)와 연결 풀 예산(100 u/s에서 약 25%)이다.
2. **사용자당 CPU 줄이기**: 08:09~08:12 프로파일의 CPU flame graph로 29ms의 함수별 몫을 본다. 후보는 Core 응답 압축(2KB 넘는 응답 gzip, P-010), Datadog 트레이서(로컬 P-016에서 트레이서가 한계를 낮췄다), 거의 바뀌지 않는 데이터의 반복 조회(P-013: 판매 정책 3번, 회차·공연·공연장 2번씩), 주문마다 Modulith 이벤트 기록(insert·update·archive insert). 29 → 20ms면 같은 사양에서 약 1.45배.
3. **Core 옆 컨테이너 옮기기**(Redis·nginx·Agent 0.24코어): 이론 한계 55 → 63 u/s(약 +15%).
4. **메모리(P-019)와 요청 스레드 수(Tomcat 200)**: 한계를 올리기보다 한계 근처에서 무너지는 정도를 줄인다.

## 측정 도구

- 틀린 것 1: `run-step.ps1 -Prod`가 `scripts/core-capacity/member-ids.txt`가 있기만 하면 개수를 보지 않고 썼다. 이 PC의 파일은 8월 Oracle 운영에서 받은 500개였다. 1,800명을 넣으면 같은 회원이 겹쳐 비즈니스 거절로 회차를 버리게 된다. 사용자 수보다 적으면 운영 DB에서 다시 받게 고쳤다(`fdc054c`, 20 u/s 실행에서 1만 개로 다시 받음). 옛 파일은 세션 임시 폴더에 복사해 뒀다.
- 틀린 것 2: 부하 발생기로 보낼 프로젝트를 tar로 묶을 때 `.agents`·`.claude`를 빼지 않았다. 이 PC의 `.agents/skills`는 없는 폴더를 가리키는 정션이라 tar가 실패했다(07:34 예열 중단). tar 제외 목록에 넣었다(`81be08e`). 정션 자체는 건드리지 않았다.
- 틀린 것 3(P-020): 실행마다 운영 DB를 끝까지 읽는 점검과 부하 중 1초마다 전체 prometheus를 받는 수집이 측정 대상을 흔들었다. 실행마다 DB에 묻지 않고, 1초 수집은 거른 지표만 받게 고쳤다(`8cb4ac9`, 위 "점검을 고친 뒤 다시 오르기").
- 참고: Datadog 컨테이너 목록의 `strange_knuth`·`eloquent_kilby` 같은 이름은 옛 점검이 실행마다 띄운 일회용 `postgres:18-alpine` psql 컨테이너다. 고친 뒤에는 `-CheckOnly`와 회원 ID를 받을 때만 뜬다.
