# 2026-10-22 운영: 요청을 줄인 코드, 데운 JVM에서 사용자당 CPU −25%, 50 u/s는 경계

## 요약

**데운 JVM으로 다시 잰 결과(08:03~08:13)가 이날의 결과다.**

- 같은 데워진 상태(JIT 실행당 1~3초)끼리 비교하면 사용자당 Core CPU가 **40 u/s 29.9 → 22.4ms(−25%)**로 줄었다. 50 u/s 호스트 CPU는 0.94~0.96 → **0.73~0.78**이다. 10-19 로컬 일지의 계산(78%)과 맞다.
- 40 u/s PASS(체류 p99 591ms, 10-19 1,046ms). **50 u/s는 FAIL 1·PASS 2**다. FAIL은 응답 시간이 아니라 "주입 끝에 남은 사용자 54명 > 50명" 하나였고, 15초마다 1~2초씩 오는 짧은 멈춤이 주입 끝과 겹쳤다. **60 u/s는 확실한 FAIL**(체류 p99 2.4초, 남음 110명, CPU 최대 1.0)이다.
- 규칙(FAIL이 한 번이면 그 부하는 FAIL)으로 첫 FAIL은 여전히 50 u/s다. 그러나 10-19의 50 u/s(남음 391~459명, p99 10~14초)와 달리 경계에 걸쳐 있다.
- 예열은 20 u/s를 세 번(JIT 13.2 → 5.3 → 1.3초) 돌려야 했다. 그중 첫 번째는 쉬는 20분 동안 스왑으로 밀려난 Core 메모리(717MB)를 다시 읽느라 느렸다(P-019).

아래 "아침 사다리(07:28~07:41)"는 덜 데워진 JVM으로 잰 것이라 코드 효과 판정에 쓰지 않는다. 처음 요약은 그대로 둔다.

### 아침 사다리 요약(덜 데워진 JVM)

요청을 줄인 코드(master `777ddf87`, 10-19 로컬에서 사용자당 Core CPU −20%)를 운영에 배포하고 5 u/s부터 사다리를 올랐다.

- **결과**: 5~40 u/s PASS, **50 u/s FAIL**(재현도 FAIL). 10-19 이전 코드와 같은 자리에서 막혔다. 원인 모양도 같다: 호스트 CPU 포화(P-017).
- 사용자 한 명이 Core에 시키는 일은 계획대로 줄었다. HTTP 5 → 3번, 저장소 호출 20 → 12번, 연결 빌림 10 → 8번, 메모리 할당 1.5 → 1.0~1.1MB.
- 그런데 **사용자당 Core CPU는 오히려 많았다**(20 u/s 29.5 → 49.6ms, 40 u/s 29.9 → 37.9ms). 늘어난 몫은 거의 다 JIT 컴파일이다.
  Core를 켠 지 4분 만에 시작해 사다리 내내 JIT이 코드를 컴파일하고 있었다. 10-19의 비교 대상은 Core를 켠 지 40분 뒤, 앞선 사다리를 한 번 돈 뒤였다.
- 그래서 **오늘 결과로는 요청 줄이기가 운영 한계를 올렸는지 판정할 수 없다.** 예열 한 번(5 u/s × 30초)으로는 운영 2 vCPU의 JVM이 데워지지 않는다(P-005 운영 근거).
- 대형 회차를 다 써서(045까지) 진단 실행은 하지 않았다.

다음 수는 사용자가 정한다. 선택지는 맨 아래 "다음에 할 일"에 있다.

## 발견한 문제

### P-005 운영: 예열 한 번으로는 JVM이 데워지지 않아, 사다리 내내 JIT이 CPU를 쓴다

**증상**: 요청을 줄인 코드의 사용자당 Core CPU가 이전 코드보다 많다. 20 u/s 49.6ms(10-19 29.5ms), 30 u/s 43.5ms(27.7ms), 40 u/s 37.9ms(29.9ms).
그래서 40 u/s 호스트 CPU가 0.89(10-19 0.78)로 이미 경계에 있었고, 50 u/s에서 넘쳤다.

**근거**

- 20 u/s 계산: Core CPU (2.8531E11 − 2.5556E11)ns ÷ 10⁶ = 29,750ms, ÷ 600명 = 49.6ms. 10-19는 (4.9561E11 − 4.779E11) ÷ 10⁶ = 17,710ms, ÷ 600 = 29.5ms.
  더 쓴 CPU 29,750 − 17,710 = 12,040ms. 같은 실행의 JIT 컴파일 차이는 (175,449 − 162,802) − (265,151 − 263,588) = 12,647 − 1,563 = 11,084ms.
  **더 쓴 CPU의 약 90%가 JIT 컴파일이다.** 20 u/s 호스트 CPU는 0.63이라 컴파일러 스레드가 CPU를 기다린 몫은 작다.
- 실행마다 JIT 컴파일 10.5~24초(5~40 u/s). 10-19 두 번째 사다리는 1.6~8.6초였다.
- C1 코드가 오늘 사다리 동안 36 → 15MB로 줄며 C2로 옮겨 갔다. 10-19 두 번째 사다리는 처음부터 10~11MB였다(이미 데워진 상태).
- C2 코드(`CodeHeap 'non-profiled nmethods'`)는 예열 7.8MB → 30 u/s 16.2MB로 계속 자랐다. 10-19는 5 u/s 때 이미 16.2MB였다.
- Core 기동: 오늘 50 u/s 때 867초. 10-19 50 u/s 때 2,621초(앞서 첫 사다리를 돌았다).

**원인 후보** (가능성 높은 순)

1. 예열 규칙이 운영에 모자라다 — `ticket/.agents/skills/core-capacity/production.md` "준비" 3("같은 Core 기동 안에서는 한 번이면 된다"), `scripts/capacity/README.md`의 예열 규칙 — 지지: 위 JIT·코드 캐시 수치, 20 u/s의 더 쓴 CPU 90%가 JIT. 반대·미확인: 2 vCPU에서 JIT이 끝나는 데 얼마나 걸리는지(부하·시간) 아직 모른다. 10-19는 41분 기동·컴파일 누적 264초에서 안정됐다.
2. 요청 줄이기의 CPU 절감이 운영에서는 작다 — 지지: JIT을 뺀 20 u/s 사용자당 CPU가 (29,750 − 12,647) ÷ 600 = 28.5ms로 10-19의 (17,710 − 1,563) ÷ 600 = 26.9ms보다 작지 않다. 반대: 덜 데워진 JVM은 C1(프로파일 수집) 코드로 돌아 앱 코드 자체가 느리다. 그래서 JIT을 뺀 값도 데워진 상태보다 크다. 로컬 같은 날 A/B(같은 데워진 상태)는 −20%였다. **데워진 상태에서 다시 재야 가린다.**

**어떻게 발견했나**

1. 실행 표에서 30 u/s부터 연결 10/10과 CPU 0.9가 나왔다. 10-19 이전 코드는 40 u/s에서 이 모양이었다. 요청을 줄였는데 더 일찍 찼다는 점이 이상했다.
2. prometheus 전후로 사용자당 CPU를 냈다. 모든 부하에서 10-19보다 많았다. 그런데 HTTP·저장소·빌림·할당은 계획대로 줄어 있었다. "일은 줄었는데 CPU는 늘었다"가 남았다.
3. 10-19 일지에서 50 u/s FAIL 때 JIT 시간이 늘었던 것을 떠올려 `jvm_compilation_time_ms_total`을 봤다. 오늘은 CPU가 남는 5~20 u/s에서도 실행마다 10~14초였다.
4. 20 u/s에서 더 쓴 CPU(12.0초)와 더 한 컴파일(11.1초)이 거의 같았다. 코드 캐시(C1·C2)가 사다리 내내 움직이는 것도 확인했다.

## C를 올릴 후보 (서버 사양 그대로, 10-22 정리)

## 측정 도구

- 예열 규칙(P-005): "20 u/s를 실행마다 JIT 3초 아래가 될 때까지"로 데웠더니 세 번 걸렸다(13.2 → 5.3 → 1.3초). 쉰 뒤 첫 번째는 스왑 읽기 때문이라 JIT 기준과 함께 "Core 메이저 폴트가 가라앉을 때까지"도 봐야 한다. 규칙 문서에 넣을지는 결정 대기.
- `local-env/seed-prod.ps1`의 `rds-prod.env`의 `EC2_HOST`가 옛 IP(`15.164.48.63`)였다. Core EC2를 켤 때마다 IP가 바뀐다(지금 `43.201.25.181`). 도메인(`oneticket.site`)을 쓰면 이 PC의 `known_hosts`에 도메인이 없어 SSH가 "Host key verification failed"로 막힌다.
  이번에는 스크립트와 같은 절차를 손으로 돌리되, 터널만 run-step 점검이 남긴 `known_hosts`(호스트 키가 옛 IP로 신뢰한 키와 같음)를 쓰게 했다. 사용자 SSH 설정은 바꾸지 않았다.
- smoke(1 u/s × 5초)는 Core 기동 343초에 돌아 주문 생성 p95 1,104ms로 FAIL 판정이 났다. smoke는 흐름 확인용(5/5 성공, 거절 0)이라 판정에 쓰지 않았다. 차가운 JVM의 첫 요청이다.
- 회차: 대형 45개 중 마지막 `920000045`까지 썼다. 진단 실행은 회차가 없어 하지 않았다. 운영 진단은 스레드 덤프가 사용자 손(`kill -3`)이라, 오늘 원인은 prometheus 전후와 Datadog 지표로 갈음했다.
- 부하 발생기 한 대로 50 u/s까지 Gatling GC 최대 16ms, 입장 흔들림 ±1명이었다. 다른 두 대는 필요 없었다.
