## 발견한 문제

### P-017 추가 근거(11-09): 사용자당 CPU가 4분의 1로 줄어 첫 FAIL이 90 u/s로 올랐고, 막는 것은 여전히 호스트 CPU다

**증상**: 90 u/s에서 모든 요청이 함께 느려졌다. Core p95가 80 u/s보다 배치도 28 → 2,000ms, 선택 62 → 358ms, 주문 134 → 500ms.

**근거**

- 사용자당 Core CPU: 25 u/s 30.1 → 50 u/s 15.9 → 80 u/s 16.8 → 90 u/s 16.0ms. 부하가 늘어도 한 명당 일은 같다. 11-05(`1546f3c4`) 같은 호스트 03-3은 55~66ms였다.
- 90 u/s × 16.0ms = 초당 1.44코어 = 2 vCPU의 72%가 Core 몫이다. `core-metrics.tsv`의 90 u/s 실행 중 `system_cpu`가 거의 매초 1.0, `process_cpu`가 0.6~0.8이다. 나머지 0.2~0.4(0.4~0.8코어)는 Core 밖(nginx·Datadog Agent·Redis·FE)이다.
- 연결 1회 점유: 80 u/s 7.1ms → 90 u/s 12.2ms, 빌림당 대기 1.0 → 26.4ms. 사용자당 빌림은 5.0 → 5.1번으로 같다. CPU가 차서 연결을 쥔 스레드가 늦게 돈 것으로 본다(10-17·10-26과 같은 꼴).
- 1초 멈춤: 80 u/s 07:53:30, 90 u/s 07:54:30·07:57:01에 `process_cpu`가 0.40·0.40·0.41로 떨어지고 그 초에 busy 73·107·171, 대기 1·52·2로 튄다. 80 u/s는 그 뒤 회복했고 90 u/s는 07:54:42·07:54:50·07:57:12에 대기 31·44·63이 다시 왔다.
- JIT이 90 u/s 실행마다 10~20초다(80 u/s 12.1초). 새 부하에서 다시 컴파일하는 CPU가 더해진다(P-005).
- 진단 실행의 기술 실패 18명은 모두 `StacklessClosedChannelException`(응답 없이 연결 닫힘)이다. 배치도 앞 `venue layout` 12, 주문 2, 나머지 4. 요청 스레드 200/200이 찬 07:57:03~04 전후로 본다(미확인). 동시 사용자 최대 835명이라 nginx FD(P-023)의 1,000명보다 적지만, WebSocket과 HTTP가 사용자마다 따로라 nginx 연결 수는 더 많다(미확인).

**원인 후보**(가능성 높은 순)

1. 호스트 CPU 2 vCPU가 Core(72%) + Core 밖 프로세스로 찬다 — 위 수치 / 반대 근거 없음. Core 밖 몫은 이번에 `docker stats`로 재지 않았다(미확인).
2. 1초 멈춤이 막힘의 계기 — 멈춘 초마다 대기가 튄다 / 원인은 여전히 미확인(11-03 프로파일러를 꺼도 그대로).
3. nginx 연결 한도 — 기술 실패가 연결 닫힘이다 / 운영 nginx 로그를 보지 못했다(미확인).

**어떻게 발견했나**

1. 90 u/s FAIL 출력에서 실패 항목이 배치도·좌석 상태 둘이고, `gatling` 요청별 p95가 모두 함께 올랐다 → 공용 자원부터 봤다.
2. 80·90 u/s `summary.json`의 `server.coreCpuMsPerUser`가 16.8·16.0으로 같은데 `processCpuMax`가 0.78 → 1.00이었다.
3. `core-metrics.tsv`를 초 단위로 놓으니 90 u/s는 `system_cpu`가 내내 1.0이고, `process_cpu`가 0.4로 떨어지는 초마다 대기·busy가 튀었다.
4. prometheus 전후 차이로 연결 점유·대기를 계산해 점유가 1.7배, 대기가 26배가 된 것을 확인했다.

**직접 보려면**

1. `distributed-results-join/capacity/20261109-075357-ladder-03-3-90ups-30s/core-metrics.tsv`를 엑셀로 연다 → `system_cpu` 열 → 07:54:29~07:54:53이 거의 모두 1.0 → 호스트 CPU가 찼다.
2. 같은 파일에서 `process_cpu`가 0.4 아래인 줄(07:54:30) → 그 줄과 다음 줄의 `hikari_pending` 52·5, `tomcat_busy` 107·113 → 멈춘 초에 밀렸다.
3. 같은 폴더 `prometheus-before.txt`·`prometheus-after.txt`에서 `hikaricp_connections_usage_seconds_sum`을 찾는다 → after 460.252 − before 291.286 = 168.966초, `_count` 84,107 − 70,205 = 13,902번 → 나누면 12.2ms(연결 1회 점유). 같은 방법으로 80 u/s 폴더(`20261109-075249-…`)는 84.593 ÷ 11,896 = 7.1ms.
4. `hikaricp_connections_acquire_seconds_sum`: 90 u/s 428.068 − 61.612 = 366.456초 ÷ 13,902 = 26.4ms(빌림당 대기).
5. `process_cpu_time_ns_total`: 90 u/s 4.3888E11 − 3.9571E11 = 43.17초 ÷ 2,700명 = 16.0ms(사용자당 Core CPU).
6. 운영 nginx 쪽(사용자가 서버에서): `sudo docker logs --since 2026-11-08T22:53:00Z --until 2026-11-08T22:58:30Z ticket-nginx 2>&1 | grep -iE "worker_connections|Too many open files|No file descriptors|\[error\]" | head` → 줄이 있으면 기술 실패 18명이 nginx 쪽이다.

**해결 선택지**

- 80 u/s를 후보로 좁히기와 15분 실행으로 간다 — 지금 코드로 내세울 숫자를 먼저 얻는다 / 차이 10이 80의 10%를 넘어 85 u/s를 한 번 더 잰다.
- Core 밖 CPU를 줄인다(Datadog Agent 끄기·FE를 다른 곳으로) — 코드 변경 없이 0.1~0.3코어를 돌려받을 수 있다(추정) / 관측을 잃거나 배포 구성이 바뀐다. 기대: 90 u/s의 `system_cpu` 1.0 구간이 줄어든다.
- 호스트를 키운다(c6i.xlarge 4 vCPU) — 가장 확실하다 / 비용, "같은 사양"의 비교가 끊긴다. 기대: 첫 FAIL이 Core 몫 72% 기준으로 약 2배.
- 사용자당 16ms 안을 더 깎는다 — 지금은 어디에 쓰는지 모른다. 프로파일러를 잠깐 켜야 한다(켜면 CPU를 30~40% 더 쓴다, 11-03).
- 1초 멈춤의 원인을 찾는다 — 멈춘 초에 `top`·`docker stats`를 1초 간격으로 남긴다(사용자가 서버에서).

**다음 실행**: 사용자가 고르면. 기본 제안은 85 u/s 한 번 → PASS면 85, FAIL이면 80을 C로 15분 실행.

### P-026 입장 속도 판정이 원격 Gatling 시작 지연을 과다 주입으로 셌다

- **증상**: 40 u/s 두 번 INVALID, "admissions/s ranged 40..58 / 40..69".
- **근거**: `booking-admissions.csv` 첫 두 초가 18+58, 8+69이고 나머지 28초는 40(한 번 41). 첫 초에 원격 Gatling이 늦게 시작해 그 초 사용자가 둘째 초로 밀렸다. 판정은 첫 초만 빼고 둘째 초부터 봤다.
- **고침**(gatling `b23094d`): 고른지는 셋째 초부터 본다. 처음 두 초의 합이 2초 분량 + 허용치를 넘으면 과다 주입으로 INVALID다. 두 실행에 적용하면 76·77 ≤ 86, 나머지 40..41로 유효.
- **결과**: 다시 잰 40 u/s(920000170) PASS, 입장 40..40.
