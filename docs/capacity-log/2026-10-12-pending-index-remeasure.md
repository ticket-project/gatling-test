# 2026-10-12 PENDING 부분 인덱스·좌석 상태 projection 재측정

## 요약

P-001(진행 중 주문 확인의 전체 스캔)을 사용자가 고르고 PENDING 부분 인덱스(`57f4db85`)를 넣은 뒤 같은 데이터로 다시 쟀다.
지난번 FAIL이던 초당 10명이 체류 p99 14.69초에서 0.11초가 되었고, 사다리는 30명까지 PASS, 40명에서 세 번 모두 FAIL이었다.
40명 FAIL의 모양은 지난번과 다르다. 느린 쿼리 하나가 아니라 DB 연결 10개가 전부 쓰이고 다섯 API가 함께 연결을 기다린다.
그런데 DB는 그 연결의 70% 이상을 "트랜잭션 중 대기(idle in transaction)"로 보내고, Core 스레드는 같은 시간에 DB 응답을 기다린다.
연결을 쥔 시간이 쿼리 실행이 아니라 그 사이 왕복과 큰 결과 전송에 쓰인다는 뜻이다. 좌석 상태 조회 한 번이 15,000행·약 1.76MB를 가져오는 것이 가장 크다(P-008, 결정 대기).
오후에 사용자가 좌석 상태를 세 열만 읽도록 고르고(`812fd552`) 다시 재니 첫 FAIL이 초당 100명으로 올라갔다. 100명 FAIL도 같은 모양(연결 10개 포화, DB는 대부분 대기)이라 P-008은 결정 대기로 남는다.

## 발견한 문제

### P-001 결과: 부분 인덱스로 해결 확인

- 같은 부하(초당 10명)에서 체류 p99 14,688ms(10-08 첫 FAIL) → 114ms, 주문 생성 Core p95 7,158ms → 22ms.
- 존재 확인 저장소 평균: 10-08 10명 922ms → 오늘 10명 0.6ms, 40명 4.6ms.
- 새 인덱스 사용 횟수 25 → 7,414(+7,389). 같은 시간 주문 생성 7,350건과 만료 worker 조회를 더한 수와 맞는다.
  `orders` 전체 스캔 횟수(`seq_scan`)는 측정 내내 8에서 늘지 않았다.
- **바인딩 값 걱정은 실측으로 해소됐다.** `status`가 `?`로 넘어가도 PostgreSQL이 매번 값을 넣은 계획을 써서 부분 인덱스를 탔다.
  `plan_cache_mode`를 바꾸면 달라질 수 있다.
- 결정: 사용자(10-12) "order에 부분인덱스 넣을게". 파일은 사용자 요청으로 Claude가 만들었다(`57f4db85`).
  보조 인덱스 0개를 고정하던 `PostgreSqlMigrationChainSchemaTest`도 허용 목록으로 같이 고쳤다.

### P-007 결과: 같은 인덱스로 만료 조회도 개선

만료 조회 `status='PENDING' AND expires_at<=now AND id>? ORDER BY id FETCH FIRST 100`이 새 부분 인덱스를 탔다.
`EXPLAIN ANALYZE` 2.276ms(10-08 292ms, 전체 스캔). 비용은 이제 주문 전체가 아니라 PENDING 수(이때 6,946건)에 비례한다.
PENDING이 많이 쌓이는 장시간 측정(03-3)에서 다시 확인한다.

### P-008 초당 40명에서 DB 연결 10개가 차고 다섯 API가 함께 연결을 기다린다

**증상**: 30명부터 연결 대기가 생기고(최대 136), 40명에서 연결 10/10, 대기 최대 243~249, Tomcat 200/200.
다섯 API의 Core p95가 함께 0.6~3.6초로 늘었다. 한 API만 느린 것이 아니다.

**근거 2: 연결을 쥔 동안 DB는 대부분 쉬고 있다**(보조 진단, `postgres-activity-sample.tsv`)

부하 구간 24개 표본, 표본마다 Core 연결 10개 중:

- `idle in transaction`(트랜잭션 안에서 Core의 다음 명령을 기다림, wait `ClientRead`) 172/240(72%), 표본당 4~9개
- `active`(쿼리 실행 중) 13/240(5%), 표본당 0~2개

`idle in transaction` 직전 쿼리는 좌석 상태 조회(`performance_seats` 전체 열 select)가 85건으로 가장 많았고, 그때 트랜잭션 나이는 평균 46ms·최대 129ms였다.
나머지는 PK 조회·insert 뒤의 짧은 대기가 고르게 섞여 있었다.

**근거 3: 같은 순간 Core 스레드는 DB 응답을 기다린다**(진단 덤프 3개, `holders.py`로 분류)

연결을 쥔 요청 스레드 대부분이 `Net.poll ← NioSocketImpl.park`(PostgreSQL 소켓 읽기 대기)에 있다.
Hibernate 행 변환(`JdbcValuesResultSetImpl`, `BasicExtractor`) 중인 스레드는 덤프마다 0~1개다.

| Hikari 연결 대기 | 19 | 101 | 144 |
| PostgreSQL JDBC(대부분 소켓 읽기 대기) | 7 | 5 | 9 |

연결 대기 위치 1위는 `PerformanceSaleFinder.requirePolicy:36`(31·38개)이다. 느린 쿼리라서가 아니라 요약·좌석 상태·선택·주문 생성이
모두 이 판매 정책 조회로 DB에 처음 들어가기 때문이다. 줄을 서는 입구다.

DB는 Core를 기다리고 Core는 DB를 기다린다. 그러면 시간은 둘 사이, 즉 왕복과 결과 전송에 쓰이고 있다.
작은 PK 조회의 저장소 평균이 10명 0.4~0.8ms에서 40명 4.3~5.0ms로 종류와 상관없이 고르게 늘어난 것도 쿼리 자체가 아니라 왕복이 느려졌다는 쪽과 맞는다.
로컬에서 5432 포트는 `wslrelay`(Docker Desktop WSL2 중계)가 받는다. 운영의 EC2 → RDS에는 이 중계가 없다.

**원인 후보** (가능성 높은 순)

1. **좌석 상태 조회가 연결을 쥔 채 15,000행·약 1.76MB를 가져온다.**
   `GetSeatStatusUseCase.java:61` → `PerformanceSeatRepository.java:27-29`(`@Transactional(readOnly = true)` 엔티티 조회, `order by s.seatId`).
   - 지지: 한가할 때 사용자당 연결 시간 55ms 중 36~42ms가 이 호출이다. `idle in transaction` 표본 1위다. 행 평균 120바이트 × 15,000행 = 1.76MB이고, 40명이면 초당 약 70MB를 DB에서 받는다.
     응답에 쓰는 열은 `id`·`seat_id`·`state` 셋인데 엔티티라 감사 열·가격·등급·버전까지 11개를 모두 읽는다.
   - 지지(측정 뒤 한가할 때 확인): 같은 SQL의 `EXPLAIN (ANALYZE, BUFFERS)`(회차 920000021)는 8.8ms였다(`Gather Merge`, 병렬 worker 2개).
     Core 저장소 평균은 한가할 때 36~42ms이므로 약 28~33ms는 DB 밖, 즉 결과 전송과 Hibernate 엔티티 변환에 쓰인다. 이 시간 동안 연결을 쥔다.
   - 반대·미확인: 표본의 나머지 절반 이상은 작은 쿼리 뒤의 대기다. 이 호출만 줄여서 얼마나 나아질지는 재측정 전까지 미확인이다.
     조회마다 병렬 worker 2개를 띄우는 비용이 Docker VM CPU에 얼마나 들어가는지도 미확인이다.
2. **로컬 DB 왕복 경로(Windows ↔ Docker WSL2 중계)가 부하가 오르면 느려진다.**
   - 지지: DB `ClientRead`와 Core 소켓 대기가 동시에 일어난다. 작은 쿼리가 종류와 상관없이 고르게 0.6ms에서 5ms로 늘었다. 5432를 `wslrelay`가 받는다.
   - 반대·미확인: 왕복 지연을 직접 재지 않았다. 중계와 VM CPU는 Windows에서 보이지 않는다. 좌석 상태의 큰 전송이 같은 경로를 막아서 생긴 결과일 수도 있다(후보 1과 겹친다).
   - 확인 방법: 부하 중에 `SELECT 1` 왕복 시간을 Windows에서 잰다. 또는 Core를 같은 Docker 네트워크의 컨테이너로 띄워 중계를 빼고 같은 부하를 잰다.
3. **사용자 한 명이 연결을 14번 빌린다(저장소 호출 21번).** 연결 10개(Hikari 기본값)에 Tomcat 200 스레드가 줄을 선다.
   - 지지: 판매 정책 `findById`가 사용자당 3번, 공연·공연 정보·공연장 `findById`가 각 2번이다(요약과 주문 생성의 표시용 스냅샷).
     왕복이 느려지면 횟수만큼 곱해진다. 대여마다 짧은 트랜잭션을 쓰는 것은 `CreateOrderUseCase` 주석의 의도된 설계다(외부 호출을 트랜잭션 밖에 둔다).
   - 반대: 한가할 때 PK 조회는 1ms 미만이라 횟수 자체가 주원인은 아니다. 왕복이 느려질 때만 커진다.
   - 확인 방법: `-PoolSize 20`으로 한 번에 하나만 바꿔 다시 잰다.
