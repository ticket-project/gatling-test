## 결론이 바뀐 과정

1. **"60 u/s에서 DB 연결 풀이 막힌다"(구간 B).**
   - 근거: 60·80 u/s에서 Hikari 대기가 쌓였고 Core CPU는 25%였다.
   - 풀을 20으로 올려 다시 재자(구간 C) 좋아지지 않았고, 같은 풀 10에서도 시간이 갈수록 나빠졌다. 기각했다.
2. **"주문이 쌓일수록 전체 스캔(P-001) 때문에 느려진다"(구간 C).**
   - 근거: 실행 계획에 `ORDERS.tableScan`이 나왔다. H2에 인덱스를 손으로 만들자 p95가 1,103ms에서 258ms가 됐다.
   - 그런데 이 숫자는 모두 Gatling 쪽이었다. 구간 D에서 DB를 비우고 주문 5건으로 재도 1,323ms가 나왔다. 주원인으로서는 기각했다. 스캔 자체는 사실이므로 P-001로 남겼다.
3. **"지연은 Core 밖, 부하 발생기에서 생긴다"(구간 D).**
   - 근거: Core 히스토그램의 실행 전후 차이로 요청별 Core 쪽 p95를 계산했다. Gatling 쪽과 10~100배 차이가 났다(P-002).

**교훈:** Gatling 숫자 하나로 Core를 판단하면 안 된다. Core 쪽 숫자, 부하 발생기 상태, 반복 실행을 같이 봐야 한다.
이 교훈이 다음 측정 규칙이 된다.

## 발견한 문제

### P-001

**주문 생성마다 같은 회원의 진행 중 주문을 인덱스 없이 전체 스캔한다** (Core·DB)

- **증상:** 구간 C에서 주문이 쌓일수록 주문 생성이 느려지는 것처럼 보였다. 지금은 대부분 P-002였던 것으로 본다.
- **근거:**
  - 주문 생성이 `OrderRepository.existsByMemberIdAndPerformanceIdAndStatus`로 같은 회원·회차의 `PENDING` 주문을 찾는다.
  - H2 `EXPLAIN ANALYZE` 결과는 `ORDERS.tableScan`, `scanCount` 13,424~14,916행, 9~34ms였다.
  - `IDX_ORDERS_MEMBER_PERFORMANCE_STATUS`는 9/29에 entity `@Index`를 지운 뒤 어느 migration에도 없다.
- **실제 영향(Core 쪽):** 구간 D 동안 주문이 5건에서 1.35만 건으로 늘었다. 그 사이 주문 생성 13,505건의 Core 쪽 시간은 누적 p50 14ms, p95 28ms 이하, p99 89ms 이하였다. 이 규모와 부하에서는 영향이 작다.
- **그래도 남기는 이유:** 운영은 주문이 지워지지 않고 계속 쌓인다. 스캔 비용은 행 수에 비례하고, 주문 생성 트랜잭션 안에서 연결을 쥔 채 일어난다. 그래서 언젠가는 드러난다.
- **해결 선택지:**
  1. `(member_id, performance_id, status)` 인덱스를 추가하는 migration을 H2·Oracle 둘 다 둔다.
     - 가장 직접적이다.
     - 쓰기마다 인덱스 갱신 비용이 조금 붙는다.
  2. 같은 확인을 Redis의 회원별 선점 정보로 한다.
     - DB 조회가 없어진다.
     - Redis와 DB가 어긋날 때의 규칙을 새로 정해야 한다.
  3. 그대로 둔다. 주문이 적은 동안은 체감이 작다.
- **운영 확인 필요:** 운영 DB에 같은 인덱스가 따로 있는지(`USER_INDEXES`)
- **결정:** 대기(사용자). 영향의 크기는 주문 수를 늘린 배경 데이터로 Core 쪽 숫자를 다시 재서 판단한다.
- **참고:** 15:37에 H2에 인덱스를 손으로 만든 것은 결정 전에 한 일이었다. 그 DB는 백업(`~/ticket-local.mv.db.bak-155338`)으로 옮겼고, 지금 DB에는 인덱스가 없다.

### P-002

**같은 PC의 Gatling이 실행 중 1~2초씩 멈춰 응답 시간이 부풀려진다** (측정 도구)

- **증상:** 같은 조건(03, 50 u/s, 같은 코드, 같은 Core)에서 체류 p95가 45ms~1,350ms로 실행마다 갈린다. 초 단위로 보면 대부분 구간은 37~42ms인데, 1~2초짜리 멈춤이 끼면 그 사이에 시작한 사용자만 1~2초가 걸린다.
- **근거:**
  - 15:57 실행에서 Core 쪽 p95와 Gatling 쪽 p95를 비교했다.

    | 요청 | Core 쪽 p95 | Gatling 쪽 p95 |
    | --- | ---: | ---: |
    | 공연 요약 | 3ms | 297ms |
    | 좌석 상태 | 28ms | 334ms |
    | 좌석 선택 | 14ms | 132ms |
    | 주문 생성 | 28ms | 212ms |
    | 주문 조회 | 2ms | 137ms |

  - 멈춘 동안 Core는 한가했다. 바쁜 스레드 1~5개, 연결 0~2개, CPU 12%였다. Core GC 멈춤은 79번 합쳐 0.48초였다.
  - 요약 단독(초당 250건)과 좌석 상태 단독(초당 50건)은 멈추지 않았다.
- **원인 후보와 판정:**

  | 후보 | 판정 | 근거 |
  | --- | --- | --- |
  | Core 처리 지연 | 아님 | Core 쪽 p95 3~28ms, 멈춘 동안 Core가 한가함 |
  | 03이 좌석 상태 응답 2,000석에 `jsonPath` 필터를 돌림 | 아님 | 끄고도 1,266ms. 필요 없는 작업이라 끈 채로 둔다 |
  | 사용자마다 결과 CSV를 전역 락 안에서 열고 쓰고 닫음 | 아님 | 쓰기를 끈 두 번이 45ms와 1,350ms로 갈림 |
  | Gatling JVM GC·safepoint 멈춤 | 아님 | GC 최대 18ms, safepoint 최대 15ms |
  | TCP 연결 재시도 | 판정 못 함 | 재전송 0을 본 실행은 멈춤이 없던 실행이었다 |
  | PC의 다른 프로세스가 CPU를 씀 | 유력 | 나빴던 16:24 실행에서 PC CPU 50~69% 중 30~40%를 Core·Gatling이 아닌 프로세스가 썼다. Defender·IntelliJ·Chrome은 아니었다. 좋았던 16:23 실행은 PC CPU 약 30% |

- **틀렸던 가설:** 16:14에 결과 CSV 쓰기를 끈 실행이 45ms로 좋게 나와 원인을 찾은 줄 알았다. 같은 조건을 한 번 더 돌리자 1,350ms가 나와 우연이었음을 알았다. 한 번의 좋은 결과로 결론을 내지 않는다.
- **우회 규칙(측정 도구에서 할 일):**
  - 판정은 Core 쪽 숫자로 한다.
  - 실행마다 유효성을 검사한다. 입장 속도가 일정한지, 클라이언트·서버 시간 차이, 부하 발생기 GC를 본다.
  - 같은 단계를 2~3번 돌린다.
  - 입장률을 정하는 측정은 부하 발생기를 분리한 환경(EC2 부하 발생기 → 운영)에서 한다.
- **결정:** 측정 도구 쪽이라 위 규칙을 다음 도구 정리에 넣는다. 원인 확정은 그 뒤 필요할 때 한다.

### P-003

**콘솔이 지난 실행의 증거 파일을 다른 실행 폴더로 복사했다** (측정 도구)

- **증상:** 좌석 상태 API 실행 폴더에 03 실행의 `booking-run-config.json`이 들어 있었다.
- **원인:**
  - Gatling은 증거 파일을 `_latest/`에 덮어쓴다.
  - 콘솔은 실행이 끝나면 `_latest/`의 파일을 결과 폴더로 복사하는데, 이번 실행이 그 파일을 썼는지 확인하지 않았다.
  - 운영 대상 결과 폴더 35개 중 20개가 이런 사본이었다. 지난 결과를 다시 볼 때 잘못 읽을 수 있었다.
- **해결:** 수정 시각이 실행 시작보다 이른 파일은 복사하지 않는다(`6c3c689`). 이미 남은 사본은 `booking-run-config.json`의 `runId`가 폴더의 `run-metadata.json`과 다르므로 구분할 수 있다.

### P-004

**IntelliJ 실행 설정과 `local-env/ticket-core.env`의 JWT secret이 다르다** (로컬 환경)

- **증상:** 15:03 점검에서 좌석 상태가 전부 401(`E1000 유효하지 않은 토큰`)이었다.
- **원인:**
  - `local-env/ticket-core-intellij.txt`의 `JWT_SECRET`(65자)과 `local-env/ticket-core.env`의 값(32자)이 다르다.
  - env 파일 값은 콘솔 기본값과 같다.
  - 어느 파일로 Core를 띄웠느냐에 따라 부하 토큰이 맞기도 하고 틀리기도 한다.
- **선택지:**
  1. 두 파일의 값을 하나로 맞춘다.
  2. 측정용 Core는 항상 env 파일로 띄운다고 정한다.
- **결정:** 대기(사용자)

### P-005

**재기동 직후 첫 부하가 크게 느리다** (Core JVM)

- **증상:** 같은 조건(풀 10, 50 u/s)에서 재기동 직후 실행은 체류 p95 7,975ms였다(15:33). 바로 다음 실행은 1,103ms였다(15:34).
- **원인 판단:** JIT 컴파일과 연결 생성 같은 예열 비용이다. 이 둘도 Gatling 쪽 숫자라 P-002가 섞였을 수 있다.
- **측정 규칙:** 기동 뒤 첫 실행은 판정에 쓰지 않는다. 예열 실행을 먼저 한다. 1 u/s × 5초로는 부족했다(15:57).
- **운영에 주는 뜻:** 티켓 오픈 직전에 배포하면 첫 사용자들이 이 비용을 맞는다.

### P-006

**IntelliJ 실행 설정이 측정에 맞지 않는다** (로컬 환경)

- **증상:** IntelliJ로 띄운 Core는 실행 방식 때문에 실제보다 느리게 잴 수 있다.
  - 디버그 실행에는 `-agentlib:jdwp`가 붙는다.
  - 일반 실행에도 `-XX:TieredStopAtLevel=1`(최적화 컴파일러 꺼짐, IntelliJ "launch optimization" 기본값)이 붙는다.
  - local 프로파일은 p6spy로 모든 SQL을 가로채 로그로 남긴다.
- **측정 규칙:** 측정용 Core는 `bootRun`으로 띄운다. `local-env/ticket-core.env`를 읽고 `DECORATOR_DATASOURCE_ENABLED=false`로 SQL 로그를 끈다.

### P-002 원인: Gatling 로그가 DEBUG였다

- **발견:** 새 스크립트로 Gatling 출력을 파일로 받아 보니, 30초 실행 출력이 10.9MB였다. 성공 요청까지
  `DEBUG io.gatling.http.engine.tx.HttpTxExecutor -- Sending request=...`가 줄마다 찍혀 있었다.
- **원인:** `load-tests/gatling`에는 logback 설정이 git 이력상 한 번도 없었다. 그래서 logback 기본값(DEBUG, 콘솔)이 쓰였다.
  콘솔 출력은 동기다. 출력이 Gradle을 거쳐 밖으로 나가는 동안 Gatling 스레드가 기다리면, 요청을 제때 보내지 못한다.
- **확인:** 같은 03 50 u/s, 같은 Core에서 비교했다.

  | Gatling 로그 | 초당 입장 | 체류 p95 / p99 | Gatling 출력 | Core 상태 |
  | --- | --- | --- | ---: | --- |
  | DEBUG(기존) | 10~101 | 5,566 / 6,941ms | 10.9MB | 연결 최대 6/10, 대기 0 |
  | WARN 1회차 | 50~50 | 47 / 119ms | 14KB | 연결 최대 4/10, 대기 0 |
  | WARN 2회차 | 49~51 | 58 / 214ms | 14KB | |

  WARN일 때 체류는 Core 쪽 요청별 p95의 합과 맞는다.
- **해결:** `load-tests/gatling/src/gatling/resources/logback.xml`을 두고 root를 WARN으로 했다(`c56f5f2`).
- **틀렸던 가설:**
  - "PC의 다른 프로세스가 CPU를 써서"는 유력하다고 적었지만 틀렸다. 같은 PC, 같은 배경 작업에서 로그만 바꾸자 멈춤이 사라졌다.
  - 출력이 콘솔로 가느냐 파일로 가느냐도 원인이 아니었다. 파일로 받았을 때도 멈췄다.
- **남은 확인:** A/A 검증(같은 실행 3번 이상)에서 계속 안정적인지 본다.

### P-006 추가: `bootRun`도 C2 컴파일러를 끈다

- 새 스크립트가 띄워진 Core의 명령줄을 보니, `bootRun`으로 띄운 Core에도 `-XX:TieredStopAtLevel=1`이 있었다.
  Spring Boot `bootRun`의 기본값(`optimizedLaunch`)이다. 오늘 구간 B~D의 측정은 모두 C2가 꺼진 Core였다.
- 운영은 jar를 `java -jar`로 띄우므로 이 옵션이 없다. 측정용 로컬 Core는 `reset-local.ps1`이 `bootJar` + `java -jar`로 띄운다.
  Core 빌드 설정(`bootRun { optimizedLaunch = false }`)을 바꿀지는 Core 쪽 결정이라 바꾸지 않았다.
- 같은 이유로 PATH의 `java`(JDK 23)로는 Core jar(Java 25 class 69)가 뜨지 않았다. 스크립트는 `~/.jdks`의 JDK 25를 쓴다.

### 도구를 만들며 고친 것

- PowerShell 5.1에서 actuator 응답(`application/vnd.spring-boot.actuator...`)은 `.Content`가 바이트 배열로 온다.
- 외부 프로그램에 빈 문자열 인자(`-password ""`)를 넘기면 5.1이 지운다. H2 Shell이 `-sql`을 비밀번호로 읽었다.
- URI 라벨의 `{performanceId}` 중괄호 때문에 히스토그램 정규식이 해당 줄을 놓쳤다.
- (10-02 아침) `Start-Process -Wait`는 자식 프로세스까지 기다린다. 재부팅 뒤 `gradlew`가 Gradle 데몬을 새로 띄우자
  `bootJar`가 끝났는데도 리셋 스크립트가 끝나지 않았다. 띄운 프로세스만 `WaitForExit()`로 기다린다.
- 표준 회차(2,000석)를 가정하지 않고 회차 ID로 좌석 시작 번호를 정한다. 실행 전 응답으로 확인하므로 대형 회차(15,000석)도 쓸 수 있다.

### 작업 중 실수

멈춘 H2 Shell을 정리하려고 "명령줄에 h2가 들어간 java"를 종료했다. 그 조건에 측정용 Core(클래스패스에 H2 jar)와
다른 Java 프로세스 하나가 걸렸다. Core는 다시 띄웠다. 다른 하나는 무엇이었는지 확인하지 못했다. 이후로는 PID를 정확히 확인한
프로세스만 끈다.
