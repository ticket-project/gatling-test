# 2026-10-25 운영 사다리: 60 u/s에서 판매 정책 캐시와 연결 풀이 서로 기다려 Core가 멈췄고, 고친 뒤에는 CPU 포화로 FAIL이다

## 요약

요청 줄이기(03이 3요청)와 로컬 캐시(판매 정책 1초, 회차 표시값 10분)가 들어간 Core `d2331055`로 운영 사다리를 5 users/sec부터 올랐다.

5~50 u/s는 모두 PASS했다. 10-19(같은 운영 사양)에는 50 u/s가 FAIL이었으니 한 단계 올랐다.
**60 u/s는 세 번 모두 FAIL**이었고, 모양이 지난번 CPU 포화(P-017)와 다르다. 연결 풀이 차는 순간 Core CPU가 오히려 0.1~0.3으로 떨어지고,
Core가 30초 단위로 멈춘다. 진단 실행 뒤에는 부하가 끝났는데도 3분 30초 동안 응답하지 않다가 한꺼번에 풀렸다.

원인은 새 판매 정책 캐시(`@Cacheable(sync = true)`)로 본다(P-022). 연결을 쥔 주문 스레드는 캐시가 채워지기를 기다리고,
캐시를 채우는 스레드는 연결을 기다린다. 캐시 적재의 DB 호출 9번이 모두 연결 대기 시간 초과(30초)로 끝났다.

사용자가 B안(`sync` 제거)을 골라 Core PR #298(`43fe8873`)로 배포했고, 대형 회차를 100개로 보충한 뒤 60 u/s를 다시 쟀다.
**멈춤은 사라졌다**(CPU가 끝까지 일하고 부하 뒤 20~40초에 회복, 적재 실패 0). 60 u/s는 여전히 세 번 모두 FAIL이고 원인은 호스트 CPU 포화(P-017)다.
첫 실행의 기술 실패는 nginx 파일 디스크립터 부족(P-023)에서 났다. 배포 직후 짧은 예열로 쟀으므로 JIT 예열 부족이 섞여 있다(추정).

다음 수는 사용자가 정한다: 50~60 사이를 좁혀 지금 사양의 C를 정할지, CPU(P-017)를 먼저 다룰지.

## 목적

10-19 운영 측정(50 u/s FAIL, P-017) 뒤 들어간 Core 변경(요청 줄이기, 판매 정책·회차 표시값 캐시, 선점 Lua 스크립트, 주문 생성 락 제거)이
운영 한계를 얼마나 옮겼는지 같은 사양에서 잰다. 03은 3요청(점유 좌석+요약 → 선택 → 주문, gatling `75701a7`)으로 운영에서 처음 돈다.

## 발견한 문제

### P-022 판매 정책 캐시와 연결 풀이 서로 기다려 Core가 멈춘다

**증상**: 60 u/s 세 번 모두, 연결 풀(10)이 차고 요청 스레드가 100~190개로 쌓이는 순간 Core CPU가 떨어지고 Core가 수십 초~3분 30초 동안 멈췄다.
멈춘 요청은 30초의 배수(60·90·120·150초)에서 500으로 끝나거나 180~212초 뒤 한꺼번에 성공했다. 50 u/s(PASS)는 연결 대기 평균 11.6ms였는데 60 u/s는 485.6ms다.

**근거**

- `core-metrics.tsv`: 60 u/s 14:23:20~21 풀 10/10·대기 36·busy 101 → 163인데 Core CPU 0.25 → 0.10, 호스트 0.30 → 0.18. 재현 14:25:31 풀 대기 383·busy 187에 Core 0.29, 호스트 0.0.
  진단 14:26:09 풀 대기 141·busy 168 뒤 지표가 3분 동안 시간 초과였다. CPU가 남는데 풀이 막혔으니 CPU가 아니라 무언가를 기다린다.
- Datadog 컨테이너 CPU: 진단 뒤 14:26:30~14:29:00에 `ticket-be` 0.03~0.09코어. 컨테이너는 재시작하지 않았다(uptime 증가).
- Datadog span `PerformanceSalesPolicyRepository.findById`(판매 정책 캐시 적재의 DB 호출), 14:20~14:31: 오류 9개, 모두 30.0~30.3초, 메시지 `Could not open JPA EntityManager for transaction`(연결을 30초 안에 못 얻음).
  60 u/s 14:23:30에 1개, 재현 14:25:00에 1개, 진단 뒤 14:26:30·27:00·27:30·28:00·28:30·29:00·29:30에 7개 연속. 14:29:30 버킷에서 성공 적재 3개가 나온 뒤 풀렸다.
- 210초 걸린 `POST /api/v1/orders` trace(14:26:08 → 14:29:38): 첫 210초 동안 하위 span이 하나도 없다. 첫 DB 호출(`MemberRepository.findActiveById`)이 +210초에 시작하고 나머지는 1초 안에 끝났다.
  주문 흐름에서 회원 조회 전에 있는 것은 트랜잭션 시작(연결 얻기)과 판매 정책 조회(캐시 적중이면 span 없음)뿐이다. 연결 얻기는 30초를 넘지 못하므로 캐시를 기다렸다.
- 점유 좌석 요청도 180~210초 동안 하위 span 없이 기다리다 200으로 끝났다. 500으로 끝난 선택·점유 좌석은 60·90·120·150초에 끝났다(`CannotCreateTransactionException`, `DataAccessResourceFailureException`).
- 전후 지표: 60 u/s 연결 대기 (5,387.93 − 142.17)초 ÷ (43,155 − 32,353)번 = 485.6ms. 50 u/s (142.17 − 37.31) ÷ (32,339 − 23,267) = 11.6ms.

**원인 후보** (가능성 높은 순)

1. 판매 정책 캐시(`sync = true`)와 연결 풀의 교착 — `ticket/src/main/java/com/ticket/booking/salespolicy/usecase/PerformanceSaleFinder.java:43`
   - 고리: 주문 생성의 `BookingPreflightReader.read`(`BookingPreflightReader.java:50`, `@Transactional(readOnly = true)`)는 시작할 때 연결을 얻고,
     그 안에서 `bookingEntryGuard.check`(`:58` → `BookingEntryGuard.java:39`)로 판매 정책 캐시를 부른다. 캐시가 막 만료되어 다른 스레드가 채우는 중이면 연결을 쥔 채 기다린다.
     점유 좌석(`GetOccupiedSeatsUseCase.java:71`)과 좌석 선택(`SelectSeatUseCase.java:47`)은 트랜잭션 밖에서 같은 캐시를 부른다. 이 스레드가 캐시를 채우게 되면
     `findById`가 새 트랜잭션을 열어 연결을 하나 더 기다린다. 연결 10개를 모두 주문 스레드가 쥐고 캐시를 기다리면, 채우는 스레드는 연결을 못 얻고 30초 뒤 실패한다.
     실패하면 기다리던 스레드 중 하나가 다시 채우기를 시도한다. 그 스레드도 트랜잭션 밖 요청이면 또 30초를 기다린다. 판매 정책은 1초마다 만료된다(`CacheConfig.java:41`).
   - 지지: 적재 실패 9번이 모두 연결 대기 시간 초과(30초)이고, 멈춘 동안 30초마다 한 번씩 연속으로 실패했다. 멈춘 동안 CPU가 거의 0이다. 주문 trace의 빈 210초.
     500 응답이 30초의 배수에서 끝났다. 성공한 적재 뒤 한꺼번에 풀렸다. 50 u/s까지는 풀이 다 차지 않아 고리가 닫히지 않았다(대기 최대 41이 2초 안에 빠짐).
   - 반대·미확인: 스레드 덤프가 없다(운영 이미지에 `jcmd` 없음). 연결 10개를 쥔 스레드가 정말 `BookingPreflightReader`에서 캐시를 기다렸는지는 직접 보지 못했다.
     "같은 키를 채우는 동안 다른 스레드가 기다린다"는 Caffeine `get(key, loader)`(내부 `ConcurrentHashMap.compute`)의 동작에 기댄 판단이다.
     트랜잭션 밖 요청이 연달아 채우기를 맡은 이유(모니터 잠금 순서)도 확인하지 못했다. 점유 좌석·선택 요청이 주문보다 두 배 많아 그럴 가능성이 크다고만 본다.
2. 호스트 CPU 포화(P-017)가 방아쇠 — 지지: 60 u/s 14:23:04~19에 호스트 CPU 0.96~1.0, 50 u/s도 평균 0.94. CPU가 차면 연결 점유가 길어져 풀이 처음으로 찬다.
   반대: CPU 포화만으로는 10-17·10-19처럼 점점 느려지고 부하가 끝나면 회복했다. 오늘처럼 CPU가 남는 채로 수 분 멈추지는 않았다.
3. 15초 간격의 짧은 정지(관찰, 원인 미확인) — 30~60 u/s 내내 약 15초마다(14:20:46, 14:21:16, 14:21:31, 14:22:16, 14:22:32, 14:23:16, 14:26:01) 1~2초 동안 풀이 차고 busy가 24~63으로 뛰며,
   Core CPU는 0.26~0.56으로 떨어지는데 호스트 CPU는 1.0이다. 1초 수집도 그때 1~2초 늦는다. 60 u/s 멈춤이 이 시점(14:23:16, 14:26:01)에서 시작했다.
   Datadog 컨테이너 CPU(10초 단위)로는 누가 썼는지 보이지 않았다.

**어떻게 발견했나**

**해결 선택지**

- A. 캐시 조회를 트랜잭션 밖으로 옮긴다: 주문 생성에서 `bookingEntryGuard.check`를 `BookingPreflightReader.read`의 트랜잭션 전에 부르고 정책을 넘긴다.

  기대: 60 u/s에서 멈춤 없이 CPU 포화로 점점 느려지는 모양(P-017)만 남고, 부하가 끝나면 바로 회복한다.
- B. `sync = true`를 뺀다: 만료 순간 놓친 요청이 각자 DB를 읽는다(1초에 한 번, 동시에 놓친 수만큼). 장점: 한 줄이고, 서로 기다리지 않아 교착이 없다.
  단점: 60 u/s면 만료 순간 수십 번 읽을 수 있다. 트랜잭션 밖 요청은 여전히 연결을 기다리지만 다른 요청을 막지는 않는다. 기대: A와 같다. 판매 정책 DB 읽기 수가 30보다 늘어난다.
- C. 요청이 적재를 기다리지 않게 미리 새로 고친다(Caffeine `refreshAfterWrite` + 비동기 적재, 새로 고치는 동안 옛 값 반환). 장점: 요청 스레드가 적재를 기다리지 않는다.
  단점: Spring `@Cacheable`만으로는 설정할 수 없어 `CacheConfig`에 로더를 두거나 캐시를 직접 써야 한다. 첫 적재는 여전히 기다린다.
- D. 유지 시간을 늘린다(1초 → 10초 등). 장점: 한 줄. 단점: 교착 기회가 10분의 1로 줄 뿐 없어지지 않고, 판매 기간·대기열 변경이 늦게 반영된다.
- E. Hikari 연결 대기 시간 초과를 줄인다(30초 → 수 초). Core 설정이다. 장점: 멈춤이 짧아진다. 단점: 원인은 그대로이고 실패 응답이 늘어난다. 다른 선택지와 함께 볼 보조 수단이다.
- 같은 모양 주의: `GetOccupiedSeatsUseCase.java:84`의 점유 목록 1초 재사용도 `ConcurrentHashMap.compute` 안에서 DB(`findReservedSeatIds`)를 읽는다. 기다리는 쪽이 연결을 쥐지 않아 교착은 아니지만,
  풀이 막히면 그 회차의 점유 좌석 요청이 모두 한 스레드의 연결 대기(최대 30초)를 함께 기다린다.

### P-022 결과: 멈춤은 사라졌고, 60 u/s는 CPU 포화로 FAIL이다

- 멈춤 없음: 세 실행 모두 `core-metrics.tsv`에서 부하 2초째부터 Core CPU 0.8~0.95, 호스트 1.0이 이어지고, 풀이 찬 채 CPU가 떨어지는 구간이 없다.
  부하가 끝나고 20~40초 안에 busy 3~13으로 돌아왔다(이전에는 3분 30초). 1초 수집의 `TIMEOUT`은 요청 스레드 200개가 모두 바빠 수집 요청이 밀린 것이다(P-009). Datadog `container.cpu.usage`도 그 구간에 1.3~1.9코어였다.
- 판매 정책 적재 실패 0(전후 지표 `state="ERROR"` 없음, 이전 9번). 30초 배수로 끝난 요청이 없다.
- 대가: 판매 정책 DB 읽기가 실행당 30번에서 129~203번(초당 4~7번)으로 늘었다. 포화 중에는 적재 한 번이 길어져 그사이 놓치는 요청이 많다. 연결 빌림 약 1만 번 중 1~2%라 한계에는 영향이 작다고 본다(미확인).
- 60 u/s가 FAIL인 원인은 호스트 CPU 포화(P-017)다. 다만 이번 60 u/s는 **배포 직후 Core**에서 5 u/s 예열(150명) 한 번 뒤에 쟀다. 14:23의 60 u/s는 같은 기동에서 사다리 5~50(약 5,100명)을 지난 뒤였다.

- **근거**: Datadog 로그 `service:nginx "No file descriptors available"` 분당 건수 14:24 6, 14:25 70, 14:26 60, 16:30 78. 메시지는 `accept4() failed (24: No file descriptors available)`와
  `socket() failed (24: …) while connecting to upstream`이고, 같은 시각 access 로그가 `500 177`이다. 남음이 801~977명이던 재현·진단(16:31~16:34)에는 없다.
  운영 서버에서 nginx 워커 `/proc/<pid>/limits`의 `Max open files`가 soft 1,024(hard 524,288)이고, 설정에 `worker_rlimit_nofile`이 없다. `worker_connections 1024`, `worker_processes auto`(워커 2개), upstream keepalive 없음.
  프록시 요청 하나가 클라이언트·upstream 연결로 파일 디스크립터 2개를 쓰므로, 워커 2개로 약 1,000개 요청이 한계다.
- **원인 판단**: Core가 먼저 밀린 뒤의 결과다. Core가 버티는 부하에서는 나지 않는다. 하지만 이때부터 실패가 Core가 아니라 nginx에서 나므로 원인을 잘못 짚기 쉽고, Queue를 켠 순간 부하(core-capacity.md 9단계)에서 회복을 방해할 수 있다.
  core-capacity.md 2단계가 말한 2026-08-04의 "nginx FD가 먼저 터졌다"와 같은 문제다.
- **어떻게 발견했나**: 재측정 60 u/s의 기술 실패가 Datadog `ticket-be` span에는 오류로 거의 없었다. 그래서 같은 시간대의 `nginx` 로그를 상태별로 세자 alert·critical이 나왔고, 메시지가 파일 디스크립터 부족이었다.
- **직접 보려면**
  1. Datadog **Logs**, `service:nginx "No file descriptors available"`, 2026-10-25 14:20~16:40 KST → 14:24~14:26과 16:30에 몰려 있다.
  2. 운영 서버에서 `docker exec ticket-nginx sh -c 'for p in $(pgrep nginx); do grep "open files" /proc/$p/limits; done'` → `Max open files 1024 524288` → 워커마다 1,024개가 상한이다.
  3. `docker exec ticket-nginx nginx -T | grep -nE 'worker_rlimit_nofile|worker_connections'` → `worker_rlimit_nofile`이 없다.
- **해결 선택지**(서버 설정, 사용자 결정)
  - `worker_rlimit_nofile`을 올리고(예: 65,535) `worker_connections`도 함께 올린다. 장점: 한 줄 설정. 단점: Core가 밀린 상태 자체는 그대로이고, 메모리를 조금 더 쓴다.
  - upstream keepalive를 켠다. 장점: upstream 연결 재사용으로 파일 디스크립터·연결 설정 비용이 준다(10-19 프로파일에서 Acceptor·Poller·`shutdown` 약 4%). 단점: 설정 확인이 더 필요하다.
  - 그대로 둔다. Queue가 Core 앞을 지키면 1,000명 밀림이 생기지 않는다는 전제다.
- **다음 실행**: 측정에는 영향이 작다(이미 FAIL인 실행에서만 난다). 바꾸면 05·06 Queue 확인 전에 반영한다.
