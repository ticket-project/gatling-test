## 발견한 문제

### P-024 좌석 배치도가 사용자마다 15,000석을 읽고 조합해 Core 시간의 72%를 쓴다

- 사실: 08:40 예열의 prometheus 전후 차이(`http_server_requests_seconds`)로 요청별 Core 시간을 나눴다.

  | 요청 | 건수 | 합계 | 평균 |
  | --- | --- | --- | --- |
  | `GET /api/v1/shows/{showId}/seats` | 150 | 124.1초 | 827ms |
  | `GET /api/v1/performances/{performanceId}/seats/status` | 193 | 29.2초 | 151ms |
  | `POST /api/v1/orders` | 130 | 8.3초 | 64ms |
  | 나머지 7종 | 785 | 14.4초 | - |

- FE는 예매 화면에 들어올 때 `useSeatMap`으로 이 API를 한 번 부르고 브라우저에 30분 둔다. 공연이 열리는 순간엔 모두 처음 들어오므로 사용자 1명 = 배치도 1번이다.
  03은 이 요청을 부르지 않아 지금까지 드러나지 않았다.
- Core `GetShowSeatMapUseCase`는 요청마다 대표 회차를 찾고, 공연장 배치·회차 좌석 15,000행을 읽어 조합한다. 결과는 모든 사용자에게 같고 좌석 상태를 담지 않는다.
- 조치: 공연별 10분 캐시(Core PR, 브랜치 `docs/scale-out-decisions-2026-11`). 캐시가 맞아도 요청마다 15,000석 JSON 직렬화는 남는다. 배포 뒤 재측정한다.

### P-025 중복 판매 판정이 Core의 생성 시각 시간대 차이로 좌석 재사용을 겹침으로 셌다

- 사실: 겹쳤다는 쌍을 운영 DB에서 읽었다. 예: 920000140 좌석 920000131, 앞 주문 08:33:54 KST 취소, 뒤 주문 08:34:05 KST 생성. 실제로는 겹치지 않는다.
- 원인: Core는 `created_at`·`updated_at`을 JPA 감사(JVM 기본 시간대, 운영 컨테이너 UTC)로, `expires_at`·`canceled_at`을 `SystemClockConfig`의
  `Asia/Seoul` 시계로 쓴다. 같은 행에서 `created_at` `2026-11-04 23:33:53`, `expires_at` `2026-11-05 08:43:53`이다. 판정 SQL이 생성 시각을 9시간 이르게 봐서
  좌석을 다시 쓴 쌍을 모두 겹침으로 셌다. 두 실행 모두 좌석 재사용이 정확히 2쌍이었다.
- 조치: 판정 SQL이 `expires_at - created_at`의 시간 단위 차이만큼 `created_at`을 옮긴다(gatling `e07dcc0`). 920000136·139·140 다시 세면 모두 0쌍.
- 남은 것: Core 데이터의 생성 시각이 전부 9시간 어긋나 있다. 감사 시각을 같은 시계로 맞출지는 사용자 결정이다.
