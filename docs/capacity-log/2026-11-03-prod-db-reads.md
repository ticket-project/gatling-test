# 2026-11-03 운영: 주문 경로 DB 읽기 두 곳을 줄인 뒤, 100 u/s가 경계로 올라왔다

## 요약

- 같은 날 프로파일러를 끈 측정([prod-profiler-off](2026-11-03-prod-profiler-off.md), Core `46a8d7d0`)에 이어, 주문 경로 DB 읽기 두 곳을 줄인 Core `278a83f9`(PR core#301)를 쟀다. 프로파일러는 계속 꺼져 있다.
- **60·80·90 u/s PASS, 100 u/s는 FAIL → FAIL → PASS**(사다리·재현·진단). 판정 규칙상 100은 FAIL이지만, 이전 코드의 100 u/s(FAIL 3번)보다 나아져 **경계**가 됐다. C 후보는 90~100 u/s다.
- 사용자 한 명당 저장소 호출 8.2~8.4 → **6.05번**, 연결 빌림 6.2~6.6 → **5.05번**. 예상(문장 3개, 빌림 1번 감소)과 맞다.
- 사용자당 Core CPU는 같은 부하끼리 약 1~2ms 줄었다(80 u/s 16.5 → 14.3ms, 100 u/s 15.8~16.3 → 14.0~15.5ms).
- 15초 주기 멈춤(P-017)은 그대로다. 100 u/s에서 무너진 실행은 이 멈춘 초 뒤에 연결 대기가 193까지 올랐다.

이전 코드는 같은 날 프로파일러만 끈 실행이다(`20261103-0838…`~`0843…`).

- 저장소 호출이 2.4번 줄었다: `OrderRepository.findById`(리스너가 주문을 다시 읽던 것)와 `SeatRepository.findAllByVenueIdAndIdIn`(좌석 라벨). 연결 빌림이 1.5번 줄었다(리스너의 읽기 트랜잭션 + 좌석 라벨이 연 트랜잭션 몫으로 추정).
- 100 u/s 세 번은 JIT이 20.7 → 6.8 → 4.0초로 줄면서 결과가 좋아졌다. 높은 부하에서 새로 데워지는 몫이 섞였다(P-005). 100은 경계로 다룬다.
- 사용자당 CPU는 부하가 클수록 줄어든다(60 u/s 18.4 → 100 u/s 14.0ms). 부하와 무관하게 도는 몫(Datadog 트레이서·Agent, 주문 청소, 지표)이 사용자 수로 나뉘는 몫으로 본다(추정).

## 판정

- 첫 FAIL은 이전 코드와 같은 100 u/s지만, 이전은 3번 모두 FAIL(남음 수백 명), 지금은 FAIL·FAIL(경계)·PASS다. **C 후보 90~100 u/s.**
- 모형: Core 밖 약 0.3코어, 사용자당 14.5ms면 100 u/s는 (100 × 0.0145 + 0.3) ÷ 2 = 88%로, PASS선(약 90%) 바로 아래다. 실측 경계와 맞는다.
