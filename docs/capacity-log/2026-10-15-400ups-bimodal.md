# 2026-10-15 같은 코드에서 400 u/s가 PASS와 FAIL로 갈린다

## 요약

PC를 다시 켠 뒤 코드를 바꾸지 않고(`a5ec3fab`) 다시 쟀다. 200·300 u/s는 PASS다.
400 u/s는 여섯 번 중 PASS 3번, FAIL 3번으로 갈렸다. 어제(10-14)는 같은 코드로 세 번 모두 FAIL이었다.

갈리는 이유는 400 u/s가 연결 풀 10개로 버틸 수 있는 경계이기 때문이다.

- 사용자 한 명이 연결을 10번 빌린다. 400 u/s면 초당 4,000번이다.
- 풀 10개가 이를 버티려면 한 번 빌린 연결을 평균 2.5ms(10 ÷ 4,000) 안에 돌려줘야 한다.
- PASS 실행은 1.34~1.39ms, FAIL 실행은 2.19~2.62ms였다.

모든 400 u/s 실행이 시작 5~7초 동안 막힌다. 그 뒤 회복하느냐가 판정을 가른다.
막힌 동안 PostgreSQL 연결 상태를 0.25초마다 찍어 PASS와 FAIL을 비교했다. 갈린 것은 **커밋의 WAL 디스크 기록을 기다리는 연결 수**다.
PASS는 2.5개였다가 회복 뒤 1.7개로 줄었다. FAIL은 3.4개에서 4.5개로 늘었다.
쿼리를 실행 중인 연결은 둘 다 0.7~1개뿐이다. Windows CPU는 둘 다 85~90%대라 판정을 가르지 않는다.

커밋 대기가 왜 실행마다 다른지는 확인하지 못했다(미확인). PG 체크포인트 시각과는 맞지 않는다.
fsync 시간을 재는 설정(`track_wal_io_timing`)이 꺼져 있다.

로컬 PC에서 400 u/s 판정은 실행마다 뒤집힌다(P-016). 다음 수는 사용자가 정한다.

  3. 회복을 막는 것은 커밋 대기다. FAIL에서는 막힌 동안 커밋을 기다리는 연결이 3.4 → 4.5개로 늘어, 풀의 거의 절반이 커밋에 묶였다.
  4. 같은 부하에서 커밋 대기가 실행마다 다른 이유는 확인하지 못했다(미확인). 커밋 하나가 fsync를 더 오래 기다렸다고 보지만 fsync 시간은 기록되지 않는다(`track_wal_io_timing` off).
     WSL2 VM의 디스크 동기화는 Windows 디스크를 거치므로 PC 상태의 영향을 받는다.
  5. 그래서 로컬 PC의 400 u/s 판정은 실행마다 뒤집힌다. 운영(RDS)의 커밋 지연은 다르므로 이 PASS/FAIL 비율을 운영에 옮기지 않는다.
- **틀린 가설·버린 것**

    그러나 07:35 PASS는 체크포인트가 시작된 순간에, 07:51 PASS는 48초 뒤에 돌았다. 07:32·07:37 FAIL은 1.5~2분 뒤였다. 맞지 않는다.

  - Windows TIME_WAIT: 07:32 FAIL은 1,608개에서 시작했다. 하지만 07:37 FAIL은 915개에서 시작했다. 판정을 가르지 않는다.
  - 비동기 리스너가 Redis 락을 기다리며 DB 연결을 쥔다: 덤프에 `TransactionInterceptor` 아래 Redis 대기 스택이 있었다. 그러나 `BookingEventListeners`는 `propagation = NOT_SUPPORTED`라 트랜잭션을 열지 않는다. 연결을 쥐지 않는다.
  - 만료 처리 겹침: 07:32·07:37 FAIL은 만료와 겹치지 않았다. 07:51 PASS는 PENDING 0에서 시작했다.

- **해결 선택지**(결정 대기)
  - A. 자주 안 바뀌는 읽기를 줄여 경계에서 벗어난다(P-013 나머지). 사용자당 빌림 10회 중 판매 정책 3·회차 2·공연 2회가 거의 안 바뀌는 데이터다.
    장점: 운영에도 그대로 효과. 단점: 판매 정책은 예매 가능 판정에 쓰여 바뀐 값이 늦게 반영될 수 있다. 기대: 400 u/s 풀 사용 54% → 30% 안팎, 여섯 번 모두 PASS.
  - B. 커밋 시간을 재서 원인을 확정한다. PG에 `track_wal_io_timing`을 켜고(DB 설정), run-step이 전후 `pg_stat_io`(wal)를 남기게 한다(측정 도구).
    장점: "FAIL은 fsync가 길었다"를 숫자로 확인. 단점: 로컬 WSL2 디스크 이야기라 운영에 옮기기 어렵다. 기대: FAIL 실행의 fsync 평균이 PASS보다 길다.
  - C. 로컬 400 u/s는 경계로 적고 넘어간다. 로컬 한계 후보를 "300 u/s 안정, 400 u/s 경계"로 두고 입장률은 운영에서 정한다. 장점: 바로 다음 단계. 단점: 원인 미확인으로 남는다.
  - D. 풀을 20으로 바꿔 다시 잰다(Core 설정). 10-12에는 1회 사용이 8 → 18ms로 늘어 효과가 없었지만 그때는 포트 중계 환경이었다.
    장점: 한 줄 실험. 단점: 커밋 대기가 원인이면 동시 커밋만 늘어 효과가 없을 수 있다.

### P-016 어떻게 발견했나

1. 07:31 400 u/s가 PASS(p99 1.48초)로 나왔다. 같은 코드로 어제는 세 번 FAIL이었다. 측정 규칙("갈리면 원인부터")대로 같은 부하를 다시 쟀고, 07:32에 FAIL(p99 13.3초)이 나왔다.

- **도구 문제(고침)**: 처음 만든 `-Datadog`은 PowerShell 세션에 `JAVA_TOOL_OPTIONS`를 남겼다. 같은 창에서 이어 돈 run-step의 Gradle(Windows Java)이 컨테이너 경로의 에이전트를 찾다 실패했다(10:06 ABORT, `Error opening zip file ... /opt/datadog/dd-java-agent.jar`). 셸 변수 이름을 `CORE_JAVA_TOOL_OPTIONS`로 나눠 고쳤다.

## 쓰기 커밋 줄이기 선택지 (P-016 다음 수, 결정 대기)

예매 한 건의 쓰기 커밋은 3번이다.

| 커밋 | 무엇을 쓰나 | 코드 |
| --- | --- | --- |
| 1. 주문 저장 | 주문·주문 좌석·선점 이력·`event_publication` 행 | `PendingOrderCreator.create`(`PendingOrderCreator.java:44`, 이벤트 발행 `:72`) |
| 2. 후처리 시작 표시 | `update event_publication set status = PROCESSING` | Spring Modulith 2.1.1 `DefaultEventPublicationRegistry.markProcessing`(`REQUIRES_NEW`, 끌 설정 없음) |
| 3. 후처리 완료 표시 | `event_publication` 삭제 + `event_publication_archive` 삽입 | `markCompleted`(`REQUIRES_NEW`), `completion-mode: archive`(`application.yml:15`) |

2·3은 `BookingEventListeners.on(OrderCreated)`(`BookingEventListeners.java:59`)를 Modulith가 감싸며 생긴다. 이 후처리는 Redis 선택 정리와 HELD WebSocket 발행이고(`HeldSeatPublisher`), 실제 점유 기준인 Redis hold는 주문 저장 전에 이미 기록돼 있다.
ADR 0003은 커밋 뒤 후처리를 이 registry로 최소 한 번 실행하도록 정했다.

| 선택지 | 바꾸는 것 | 커밋/건 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| A. 주문 요청 안에서 커밋 뒤 바로 후처리 | `OrderCreated` 발행을 빼고 `CreateOrderUseCase`(주문 저장 뒤, 트랜잭션 밖)에서 `HeldSeatPublisher`를 직접 부른다 | 3 → 1 | 커밋 3분의 2 감소. 연결 빌림도 3번 감소(선점 정보 읽기·시작·완료). 비동기 스레드 폭증(P-015)도 OrderCreated 몫은 사라진다 | ADR 0003의 "최소 한 번"을 OrderCreated에서 포기. 후처리가 실패하면 재시도 없이 선택은 TTL(5분)로 사라지고 HELD 알림은 빠진다. 주문 응답이 Redis 작업 몇 ms만큼 늦어진다 |
| B. 후처리 기록 커밋만 디스크 확정을 기다리지 않게 | Modulith의 2·3 트랜잭션에만 `SET LOCAL synchronous_commit = off` | 3(이 중 2번은 fsync 안 기다림) | 기록·재시도 보장은 유지. 주문 커밋은 그대로 안전 | 라이브러리 안쪽 트랜잭션에 끼어들어야 해서 구현이 까다롭고 업그레이드에 약하다. DB가 죽으면 직전 1초 미만의 완료 표시가 사라져 재처리(중복 HELD 알림 가능) |
| C. 완료 표시를 보관 대신 삭제로 | `completion-mode: delete` | 3(완료 커밋이 가벼워짐) | 설정 한 줄. 완료 커밋의 WAL이 줄어든다 | 커밋 횟수는 그대로라 효과가 작다. 완료 이력(30일 보관)이 없어진다 |
| D. DB가 커밋을 더 묶게 | PostgreSQL `commit_delay`·`commit_siblings` | 3 | 코드 변경 없음, 바로 실험 가능 | 효과 미확인. 부하가 낮을 때 커밋마다 지연이 조금 늘어난다. 운영 RDS 파라미터 그룹도 바꿔야 한다 |

- 기대 효과는 미확인이다. 주문 저장 커밋이 가장 크므로(행 4종) 커밋 수가 3분의 1이 돼도 WAL 바이트는 그만큼 줄지 않는다. 고친 뒤 같은 조건(풀 10, 트레이서 끔, PENDING 0)으로 450·500 u/s를 다시 잰다.

## P-013 추가 근거(10-15)

- 사용자당 빌림은 10.0회로 어제와 같다(저장소 호출 상위: 판매 정책 `findById` 3회, 회차 `findById` 2회, 공연 `findById` 2회).
- 10-14의 "연결 1회 1.7 → 2.4ms로 늘어난 이유 미확인"에 답이 생겼다. 늘어난 실행은 막힌 상태를 못 벗어난 실행이고, 그 실행에서는 WAL 커밋 대기가 연결 시간의 절반 가까이를 차지했다. 1회 사용은 막힘의 원인이자 결과다.
- 풀 예산 식: 부하(u/s) × 사용자당 빌림 × 1회 사용 ≤ 풀 크기. 400 × 10 × 1.34ms = 5.4 → 풀 10의 54%. 400 × 10 × 2.62ms = 10.5 → 105%.
