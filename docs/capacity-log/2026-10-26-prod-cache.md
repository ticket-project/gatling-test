# 2026-10-26 운영: 판정·표시값 캐시 뒤 60 u/s PASS, 80 u/s는 다시 호스트 CPU

## 요약

- 판매 정책 1초·회차 표시값 10분 캐시(Core `43fe8873`)를 운영에서 쟀다. 데이터·설정·시나리오는 10-22와 같고 Core 코드만 바뀌었다.
- **5~60 u/s PASS, 80 u/s FAIL 3번**(사다리·재현·진단). 10-22 데운 JVM에서 FAIL이던 60 u/s(남음 110명, 체류 p99 2.4초)가 오늘은 PASS(남음 2명, 1.3초)다. 첫 FAIL이 50~60에서 80으로 올라 **C 후보는 60~80 u/s**다.
- 캐시가 줄인 것은 CPU보다 DB 연결이다. 사용자당 저장소 호출 12.0 → 8.6번, 연결 빌림 8.0 → 6.8번, 60 u/s 연결 대기 평균 48.5 → 15.8ms. 사용자당 Core CPU는 60 u/s 24.0 → 22.2ms(−7.5%), 50 u/s 22.7 → 22.2ms(−2%)로 조금 줄었다.
- 80 u/s에서 막힌 곳은 다시 호스트 CPU(P-017)다. Core만 80 × 22.2ms = 1.78코어가 필요하고 nginx·Redis·Agent 약 0.3코어를 더하면 2 vCPU를 넘는다. CPU가 차자 연결 1회 점유가 10 → 21ms로 늘어 풀(10)이 117% 차고, 요청 스레드 200개가 다 찼다. 그 뒤로 스왑 폴트(P-019)와 nginx FD 고갈(P-022, 새로 발견)이 따라왔다.
- 차가운 JVM을 데우는 데 20 u/s 예열이 8번 걸렸다(JIT 59.3 → 2.8초).

## 목적

10-22 "C를 올릴 후보" 중 "반복 읽기 줄이기"를 사용자가 넣었다. 판매 정책은 판정용이라 1초, 회차 단위 표시값은 10분 재사용한다(사용자 결정 10-22).

## 판정

- 80 u/s는 사다리·재현·진단 세 번 모두 FAIL이다. 60 u/s는 한 번 재서 PASS다. **C 후보는 60~80 u/s**이고, 좁히기(5단계)는 사용자 결정이다.
- 10-22 추정(C 약 58)보다 높다. 추정은 CPU만 봤다. 실제로 CPU는 덜 줄었지만(사용자당 −0.5~1.8ms), 연결을 덜 빌려 15초 주기 멈춤 때 풀이 덜 막혔다. 10-22 60 u/s는 대기 평균 48.5ms에서 FAIL, 오늘은 15.8ms에서 PASS다.
- 오늘 숫자로 다시 세운 모형: Core 밖 약 0.3코어, 사용자당 22.2ms면 70 u/s는 (70 × 0.0222 + 0.3) ÷ 2 = 93%, 80 u/s는 104%다. 첫 FAIL은 70 근처로 본다(미확인).

## 발견한 문제

### P-017 추가 근거(10-26): 80 u/s에서 호스트 CPU가 차고, 연결 점유가 두 배가 되어 풀 10이 막힌다

**증상**: 80 u/s에서 세 요청이 함께 느려졌다. Core 쪽 p50이 60 u/s 대비 좌석 3 → 45ms, 선택 11 → 179ms, 주문 34 → 626ms. 주입 끝 남은 사용자 606·936·1,080명.

**근거**

- 1초 지표(`20261026-075711-ladder-80ups-30s/core-metrics.tsv`): 07:57:39부터 `system_cpu`가 1.00에 붙는다. 07:57:46에 바쁜 스레드 45 → 118, 07:57:48에 연결 대기 167·바쁜 스레드 193, 07:57:50부터 200.
- 연결 1회 점유 10.02ms(60) → 20.94ms(80). 빌림 횟수는 6.82 → 6.96으로 거의 같다. 쿼리 수가 아니라 연결을 쥔 스레드가 CPU를 못 받아 오래 쥔다.
- 풀 사용률 80 × 6.96 × 20.94ms = 11.66초/초 → 연결 10개의 117%. 연결 대기 평균 357ms.
- Datadog: 같은 시간 호스트 96~98%, 그중 `ticket-be` 1.38~1.68코어.

**원인 후보** (가능성 높은 순)

1. 2 vCPU에 Core 1.78코어 + 옆 프로세스 0.3코어가 들어가지 않는다 — 운영 호스트 사양, 같은 호스트의 nginx·Redis·Datadog Agent·FE — 지지: 위 계산과 Datadog 컨테이너 CPU / 반대: 없음
2. 15초 주기 멈춤이 마지막 여유를 먹는다 — 아래 "15초 주기 멈춤" — 지지: 07:57:46(15초 주기)에 바쁜 스레드가 118로 뛰고 회복하지 못함 / 반대: 멈춤이 없어도 80 u/s는 104%라 막힌다
3. 막힌 뒤 JIT이 다시 돈다 — 지지: 80 u/s JIT 22~33초(60 u/s 8.7초) / 반대·미확인: `jvm_compilation_time_ms`는 경과 시간이라 CPU가 모자라면 함께 늘어난다. 결과인지 원인인지 가르지 못했다

**어떻게 발견했나**

1. 80 u/s `summary.json`에서 세 요청의 Core p50이 함께 오른 것을 보고 공용 자원부터 봤다.
2. `core-metrics.tsv`에서 `system_cpu`가 1.00에 붙은 07:57:39 뒤로 `hikari_pending`과 `tomcat_busy`가 늘었다.
3. prometheus 전후 차이로 빌림 횟수는 같고 1회 점유만 두 배가 된 것을 확인했다.
4. Datadog `container.cpu.usage`로 CPU를 쓴 것이 `ticket-be`이고 옆 컨테이너는 0.3코어 안팎인 것을 확인했다.

**직접 보려면**

1. `distributed-results-join/capacity/20261026-075711-ladder-80ups-30s/core-metrics.tsv`를 엑셀로 연다 → `system_cpu` 열 → 07:57:39부터 1.00 → 같은 줄 `hikari_pending`이 22 → 46 → 167로 늘고 `tomcat_busy`가 200에 닿는다. CPU가 다 차서 요청이 쌓였다는 뜻이다.
2. 같은 폴더의 `prometheus-before.txt`·`prometheus-after.txt`에서 `hikaricp_connections_usage_seconds_sum`과 `_count`를 찾는다 → after − before가 349.63초, 16,698번 → 나누면 20.94ms. 60 u/s 폴더(`20261026-075605-ladder-60ups-30s`)는 122.98초 ÷ 12,270번 = 10.02ms. 연결 한 번을 두 배 오래 쥐었다.
3. 같은 방법으로 `hikaricp_connections_acquire_seconds`를 보면 5,971.37초 ÷ 16,710번 = 357ms(60 u/s 193.48 ÷ 12,270 = 15.8ms). 요청이 연결을 기다린 평균이다.
4. Datadog **Infrastructure → Containers**(또는 Metrics Explorer `sum:container.cpu.usage{*} by {container_name}`), 2026-10-26 07:55~08:02 KST → `ticket-be`가 1.2~1.7코어, 나머지는 0.1 안팎이다.

**해결 선택지**

- nginx upstream keepalive(사용자, 운영 설정) — 요청마다 새 TCP 연결을 없앤다. P-022도 줄인다 / 효과 작음(10-22 추정 −3~4%) / 사용자당 CPU 22.2 → 약 21.4ms, C 약 +3

### P-022 동시 사용자가 1,100명대로 쌓이면 nginx 파일 디스크립터가 바닥나 연결을 끊고 500을 낸다

**증상**: 80 u/s 진단 실행에서 2,400명 중 189명이 기술 실패(7.9%)다. Gatling 연결 끊김(`StacklessClosedChannelException`) 167건, HTTP 500 22건(좌석 15, 선택 4, 주문 3).

**근거**

- nginx 에러 로그(Datadog `service:nginx`): 08:00:23 KST부터 두 워커(`22#22`, `23#23`) 모두 `accept4() failed (24: No file descriptors available)`.
- 같은 초의 nginx 접근 로그에 `3.36.45.88 … 500 177`. 본문 177바이트는 nginx 기본 오류 페이지라 Core가 아니라 nginx가 낸 500이다.
- 진단 실행의 최대 동시 사용자 1,129명. 사용자마다 nginx에 클라이언트 연결 하나, 요청마다 Core로 가는 upstream 연결 하나(keepalive 없음, 10-22 확인)라 워커 두 개의 FD가 모자란다.
- 사다리·재현(최대 606·936명)에서는 나지 않았다.

**원인 후보**

1. nginx 워커의 열린 파일 수 한도(soft `nofile`)가 연결 수보다 작다 — 운영 `nginx.conf`(저장소 밖), `worker_rlimit_nofile` 없음으로 봄 — 지지: 오류 번호 24(EMFILE) / 미확인: 실제 한도 값(`/proc/<nginx 워커 PID>/limits`)
2. upstream keepalive가 없어 요청마다 FD를 하나 더 쓴다 — 10-22 `nginx -T` — 지지: 설정 / 반대: 단독으로는 한도를 정하지 않는다

이 문제는 C를 정하지 않는다. Core가 이미 막혀 동시 사용자가 1,000명을 넘은 뒤에야 난다. 그러나 실제 몰림에서 Core가 잠깐 느려지면 느림이 오류로 바뀌는 지점이다. 8월 부하 테스트(`loadtest 2026-08-04`)에서도 nginx FD 고갈이 있었다.

**어떻게 발견했나**: 진단 실행 `summary.json`의 기술 실패 7.875%를 보고 `booking-results.csv`의 `result`를 셌다(연결 끊김·HTTP 500). 500이 Core에서 났는지 보려고 Datadog 로그를 시간대로 검색했는데 Core 오류 로그는 없고 nginx 로그에 `accept4() failed (24…)`가 있었다.

**직접 보려면**

1. `20261026-075950-diag-80ups-30s/booking-results.csv`를 엑셀로 열고 `result` 열을 필터한다 → `TECHNICAL_SEAT_STATUS_NO_RESPONSE` 110, `TECHNICAL_SELECT_SEAT_NO_RESPONSE` 39, `TECHNICAL_CREATE_ORDER_NO_RESPONSE` 18, `…_HTTP_500` 22.
2. Datadog **Logs**, 2026-10-26 07:59~08:02 KST, 검색 `service:nginx "No file descriptors"` → 08:00:23부터 `[crit] accept4() failed (24: No file descriptors available)`.
3. 운영 호스트에서 `docker exec ticket-nginx sh -c 'cat /proc/$(pgrep -f "nginx: worker" | head -1)/limits | grep "open files"'` → 워커 한도. `worker_connections 1024`보다 작으면 이 문제다.

**해결 선택지**

- nginx `worker_rlimit_nofile`을 올리고 컨테이너 `ulimits.nofile`을 맞춘다(사용자, 운영 설정) — 몇 줄 / 메모리 조금 / 진단 실행의 연결 끊김·500이 사라지고 밀림만 남는다
- upstream keepalive(P-017 선택지와 같음) — FD와 CPU를 함께 줄인다 / 설정 확인 필요(WebSocket `Connection` 헤더 분리)
- 지금은 두고 Queue 입장률로 동시 사용자를 막는다 — 변경 없음 / Core가 잠깐 느려지는 순간에는 막지 못한다

## 측정 도구

- **Git Bash에서 `run-step.ps1`을 띄우면 원격 부하 발생기 준비가 실패한다.** `scripts/distributed-common.ps1`의 `Resolve-CommandPath`가 PATH를 먼저 보므로, Git Bash가 넘긴 PATH의 GNU `tar`(`/usr/bin/tar`)를 잡는다.
  GNU tar는 `C:\…\gatling-test-project.tgz`의 `C:`를 원격 호스트로 읽고 `Cannot connect to C: resolve failed`로 끝난다(07:36). 07:24 첫 시도는 같은 단계에서 출력 없이 10분 넘게 멈춰 끊었다.
  두 번 모두 부하가 나가기 전이라 회차 `920000070`은 깨끗했고 그대로 다시 썼다. PowerShell에서 띄우면 Windows `tar.exe`를 잡아 정상이다. 측정 숫자에는 영향이 없다.
  고치려면 `Resolve-WindowsCommandPath`가 System32 후보를 PATH보다 먼저 보게 한다(결정 대기).
- 진단 실행은 기술 실패 assertion으로 Gatling이 끝나 HTML 리포트 통계가 비었다(`requests` 없음). 판정은 기술 실패율·밀림으로 났으므로 영향 없다.
- 운영 진단의 스레드 덤프(`kill -3`)는 하지 않았다. 원인은 prometheus 전후, 1초 지표, Datadog 컨테이너 CPU·로그로 갈음했다.
