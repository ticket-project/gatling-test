# Ticket Gatling 개발 기준

## 커밋과 PR 컨벤션

커밋 메시지와 PR 제목은 Conventional Commits를 기반으로 작성한다. 이 규칙은 사람과 AI 에이전트 모두에게 동일하게 적용한다.

### 기본 형식

```text
<type>(<scope>): <한국어 설명>
```

`scope`는 선택 사항이다.

```text
test(load): 주문 상태 조회 부하 시나리오 추가
feat(console): 분산 실행 결과 미리보기 추가
fix(distributed): 노드별 feeder 분할 오류 수정
refactor(report): 증거 파일 집계 책임 분리
perf(load): 결과 기록 동기화 비용 축소
docs: 커밋 및 PR 컨벤션 문서화
```

### type

`type`은 변경 파일의 종류가 아니라 변경 목적을 기준으로 선택한다.

| type | 사용 기준 |
| --- | --- |
| `feat` | 콘솔, 실행기 등 사용자가 이용하는 새로운 기능 추가 |
| `fix` | simulation, 실행기, 결과 집계의 잘못된 동작 수정 |
| `refactor` | 동작과 측정 의미를 유지하는 코드 구조 개선 |
| `perf` | 부하 발생기나 결과 처리 자체의 성능 개선 |
| `test` | simulation, assertion, 부하 모델, 증거 수집 변경 |
| `docs` | 문서만 변경 |
| `chore` | 제품 동작과 무관한 유지보수 작업 |
| `build` | Gradle, 의존성 또는 빌드 설정 변경 |
| `ci` | CI 워크플로우 변경 |
| `security` | token, secret 또는 민감 정보 취급 강화 |
| `revert` | 기존 변경 되돌리기 |

부하 테스트 저장소에서는 simulation이나 합격 조건을 추가·변경하는 작업에 `test`를 우선 사용한다. 콘솔이나 실행기에 새로운 사용자 기능을 추가할 때는 `feat`를 사용한다.

### scope

`scope`는 변경의 주된 책임 영역을 나타낸다. 가장 작은 적절한 범위를 선택한다.

1. Gatling simulation과 부하 모델은 `load`를 사용한다.
2. 로컬 실행 UI와 명령 생성은 `console`을 사용한다.
3. 분산 실행과 노드 제어는 `distributed`를 사용한다.
4. 결과·증거 집계는 `report` 또는 `evidence`를 사용한다.
5. 특정 대상 흐름이 중심이면 `booking`, `queue`, `core`를 사용할 수 있다.
6. 특정 범위를 정하기 어려운 저장소 전체 작업은 scope를 생략한다.

권장 scope:

```text
load, console, distributed, report, evidence, booking, queue, core, ci, docs
```

기존 scope로 표현할 수 있으면 새로운 scope를 임의로 만들지 않는다. 새 scope가 필요하면 실제 하위 프로젝트나 안정적인 책임 이름을 사용한다.

### 설명과 본문

- 설명은 한국어로 작성하고 마침표를 붙이지 않는다.
- `Gatling`, `Redis`, `JWT`, `CSV`, `p95`, `p99` 같은 기술 용어는 원문 표기를 허용한다.
- `수정`, `개선`, `작업`처럼 대상이 드러나지 않는 표현만 사용하지 않는다.
- 어떤 시나리오, 지표 또는 실행 흐름이 어떻게 달라지는지 드러나게 작성한다.
- simulation, 콘솔, 분산 실행기처럼 독립적인 책임은 가능한 한 별도 커밋으로 나눈다.

측정 의미나 합격 기준이 달라지는 경우 본문에 이유와 해석 변화를 적는다.

```text
test(load): Core 입장 용량 측정에 사용자 생각 시간 반영

생각 시간이 없는 비현실적인 요청 집중을 피하고 실제 사용자 흐름에
가까운 안전 입장률을 측정하도록 좌석 선택과 주문 전 대기를 추가한다.
```

호환성을 깨는 옵션 또는 결과 형식 변경은 type 또는 scope 뒤에 `!`를 붙이고 본문 하단에 `BREAKING CHANGE:`를 작성한다.

### PR

- PR 제목도 `<type>(<scope>): <한국어 설명>` 형식을 사용한다.
- type과 scope는 PR 전체의 주된 목적과 측정 대상을 기준으로 선택한다.
- simulation과 관련 문서가 함께 바뀌면 주된 목적에 따라 `test`를 사용한다.
- 서로 관계없는 시나리오, 콘솔 기능, 실행기 수정이 섞이면 PR을 분리한다.
- PR 본문에는 대상 API, 부하 모델, 합격 조건, 결과 형식, 실행 여부와 해석상 주의점을 기록한다.

### AI 에이전트 작업 규칙

- 기존 히스토리를 추측만으로 모방하지 말고 이 문서의 type, scope, 언어 규칙을 우선 적용한다.
- type은 변경 목적, scope는 주된 책임 영역을 기준으로 선택한다.
- 여러 커밋을 만들 때는 simulation, 콘솔, 실행기, 문서 책임별로 분리한다.
- 사용자가 커밋을 명시적으로 요청하지 않으면 커밋하지 않는다.
- 실제 부하 테스트는 대상과 규모를 사용자에게 확인하기 전에는 실행하지 않는다.
- 이미 푸시한 커밋 메시지를 변경하려면 영향과 이력 변경을 설명하고 사용자 승인 후 진행한다.
- force push가 필요하면 원격이 예상한 상태일 때만 갱신하는 `--force-with-lease`를 사용한다.
